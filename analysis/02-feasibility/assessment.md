# 100% 重写可行性评估

## 结论

技术上可行，但“100%”必须定义为可验证的兼容目标。

建议定义为：

- 新程序不加载或执行原 `swd3.exe`。
- 新程序不依赖 DirectDraw、DirectInput、Miles 和旧 Bink DLL。
- 原始游戏数据不需要批量转换即可运行。
- 原有剧情、地图、战斗、菜单、物品、法术、音效、音乐和动画均可到达。
- 可以读取已有 `.sav`。
- 固定逻辑在相同输入和随机种子下产生相同结果。
- 原程序的游戏逻辑 BUG 、整数截断和可重现的边界行为也纳入 1:1 规格，不主动修复。
- 画面允许在最终显示时缩放，但内部坐标、像素规则和 UI 布局保持 640×480 语义。
- 现代 Windows x64 环境不需要兼容层即可运行。

用户已确定“100%”包括原始游戏逻辑 BUG。未定义行为不能凭名称泛化处理：对能在原程序上稳定重现的输入，以动态结果作兼容规格；对只会阻断启动或新系统运行的平台问题，允许在适配层做最小修正。所有其他可观察差异都必须列入差分验证，不得当作“顺手修 BUG”。

## 为什么可行

### 代码边界完整

程序入口、主循环、窗口过程和所有外部 API 都已定位。程序没有动态下载代码，也没有观察到加壳或运行时解密整个代码段的行为。

### 数据大多外置

剧情、地图、角色、动作、图像、音效、音乐、动画和存档均有外部文件。重写的核心是兼容读取这些文件，而不是从 EXE 中重新制作全部内容。

### 平台层可替换

DirectDraw、DirectInput、Miles、Bink 和 Win32 文件映射都有清晰调用边界，可分别替换为 SDL3、FFmpeg 和标准文件 I/O。

### 渲染目标简单明确

原内部画面是固定 640×480、16 位软件缓冲区。现代 GPU 只需要负责把最终帧呈现到窗口，不需要一开始就复刻旧 DirectDraw surface 行为。

## 为什么不能直接开始完整实现

IDA 伪码丢失了以下信息：

- 原始类名、字段名和枚举名
- 大部分结构体边界
- 部分有符号/无符号类型
- union、bitfield 和继承关系
- 宏、内联函数和编译期常量的来源
- 业务函数的语义名称

直接逐函数翻译会把错误类型和错误结构固化到新代码里，而且无法证明逻辑完整。

正确顺序必须是：证据归类、格式规格、子系统规格、可执行小验证、最后才是正式实现。

## 可行性门槛

进入完整实现前，至少应满足：

1. LZO1X 兼容解压器能正确处理所有已知压缩块。
2. `.tsw` 与 `.act` 能按编号稳定定位并解析资源。
3. `huge.lmf` 能列出全部地图并解析一个完整地图。
4. 剧情解释器的 opcode 表、参数长度和等待规则已形成规格。
5. `.Ani` 至少能解出全部帧并确认时间基准。
6. 16 位像素格式、透明色和混合规则已确认。
7. 一个旧存档可以完整解析并重新序列化。
8. 原程序的关键场景可以形成重复执行的对照样本。

在这些门槛之前，只能说“具备重写条件”，不能说“已经能够保证 100%”。

## 技术风险等级

高风险：

- 剧情/场景 opcode 解释器
- 战斗状态机
- 自定义 `.Ani`
- 像素级混合与特效

中风险：

- `.tsw`/`.act` 资源关联
- `huge.lmf` 地图块
- 存档全字段兼容
- 音频并发、循环和音量规则
- 帧时序与输入边沿

低风险：

- 窗口创建
- 键鼠输入采集
- 最终画面缩放和呈现
- Bink/MP3 基础解码
- 普通文件读写
