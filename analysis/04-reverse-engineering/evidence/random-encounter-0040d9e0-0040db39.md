# 随机遇敌数据、选择与战斗切入汇编证据

状态：`assembly_exact`、`implemented`、`unit_tested`、`real_asset_verified`

唯一行为真值：`swd3.exe.lst`。

覆盖范围：

- `0x0040D9E0..0x0040DA53`：当前地图遇敌区域链建立；
- `0x0040E672..0x0040E73A`：遇敌阈值运行时表建立；
- `0x0040DA60..0x0040DB39`：随机遇敌选择；
- `0x00403F43..0x0040406F`：普通世界遇敌门与立即战斗切入。

锁定输入：

- `swd3.exe.lst` SHA-256：`701732b5481ba34876b62ca97535c9463f65ec3feb2ed745c03772dd4bc3ad8b`
- `MAPS.DAT` SHA-256：`a6faee71c0cb41c1be94f29152deed12ed19eb3e1842fb0f10e13e00132a20ba`

## 1. MAPS 载荷入口

`MAPS.DAT` 的前 `0x200` 字节属于文件前缀，`dword_4C9A10` 指向其后的原样载荷。
本单元使用载荷头两个相对偏移：

| 载荷头字段 | 目标 |
|---:|---|
| `+0x1C` | 14 字节遇敌区域源记录序列 |
| `+0x48` | 16 位遇敌阈值字序列 |

所有后续候选列表偏移同样相对该载荷基址，不相对整个文件。

## 2. 阈值表物理布局

`0x0040E672` 从 `base + u32(base + 0x48)` 开始逐个扫描 `u16`，直到遇到
`0xFFFF`。扫描到的字数保存在 `EBX`：

1. 运行时块首字写 `word_count / 8`；
2. `BL & 7 != 0` 时走原诊断分支，不复制记录；
3. 正常时每次复制连续 16 字节，直到源端下一个 `u16` 为 `0xFFFF`。

因此运行时逻辑布局是：

```text
+0x00  u16 group_count
+0x02  group[0] = 4 × { i16 step_span, i16 probability_threshold }
+0x12  group[1]
...
```

`0x0040C4E7..0x0040C514` 在装载地图时检查地图给出的遇敌组编号。如果它大于
`group_count`，原程序报告诊断并把编号改为 `1`。编号 `0` 则由选择函数明确表示禁用。

当前游戏数据 `MAPS.DAT` 的阈值源有 88 个非终止字，即 11 个完整分组。

## 3. 区域源记录与链表顺序

`0x0040D9E0` 从 `base + u32(base + 0x1C)` 扫描以下 14 字节记录：

| 偏移 | 类型 | 含义 |
|---:|---:|---|
| `+0x00` | `u16` | 地图编号；`0xFFFF` 结束整个序列 |
| `+0x02` | `u16` | 最小 tile X |
| `+0x04` | `u16` | 最小 tile Y |
| `+0x06` | `u16` | 最大 tile X |
| `+0x08` | `u16` | 最大 tile Y |
| `+0x0A` | `u32` | 候选战斗列表相对 MAPS 载荷的偏移 |

只为地图编号等于当前 `ArgList` 的记录分配 24 字节运行时节点。四个边界先零扩展到
32 位；节点 `+0x10` 保存候选偏移，`+0x14` 保存 next。每个新节点都插到
`unk_4A9A18 + 0x14` 的链头，所以选择时看到的顺序与物理源记录顺序相反。

现代实现用 `std::vector<LegacyEncounterRegion>` 表示这个链，但装载器显式反转匹配记录，
不改变“第一个命中区域”的原顺序。

当前游戏数据载荷共有 115 条区域源记录。测试遍历全部 `u16` 地图编号后确认 115 条均可
到达，所有候选偏移都在载荷内，候选数量均非零且完整。地图 37 的固定向量为
`(0,0)..(105,110)`，候选偏移 `0x20CE`，候选列表为 `{1,2}`。

## 4. `0x0040DA60` 精确选择顺序

参数是当前遇敌计数和 force 值。控制流严格如下：

1. 遇敌组编号为零时立即返回零，不消费 RNG。
2. 先解析受控角色地址，但此时不读取角色字段。
3. 调用 `sub_439070(100)`；第一次 RNG 已经发生。
4. 以 `base + group_index * 16 - 14` 取得一基分组的首个 band。
5. 最多四次将有符号 `step_span` 加到 32 位累计值；使用有符号
   `encounter_counter < cumulative` 选择 band。
6. 每次累计比较失败后都检查 `force == 1`；因此 force 恰好为一时总是选择第零 band。
   其他非零值不具有 force 语义。
7. 使用有符号严格比较 `probability_threshold > probability_roll`。不满足时仅
   `force == 1` 可以继续。
8. 通过后才读取玩家坐标，以逻辑右移四位得到 tile X/Y。
9. 按链表顺序执行四个有符号、包含边界的矩形比较，选择第一个命中节点。
10. 读取 `u16 candidate_count`，调用 `sub_439070(candidate_count)`。
11. 第二次 RNG 返回后先清零遇敌计数，再读取
    `u16 [candidate_base + 2 + random_index * 2]` 作为战斗编号。

所以以下未遇敌路径也有不同的随机副作用：

- 组编号为零：零次 RNG；
- 概率失败、四个 band 均未选中或没有区域命中：一次 `rand(100)`；
- 进入候选列表：两次 bounded RNG，并在第二次返回后清零计数。

候选数量为零时，原 `sub_439070(0)` 会在计算接受上限时产生整数除零。当前合法资产没有
该状态。现代受检边界返回
`candidate_count_zero_original_divide_error`，不会把它悄悄解释成“无遇敌”，也不会执行
宿主未定义行为。候选载荷截断的受检路径仍先消费第二次 RNG、清零计数，再报告原读取点
越界，保留故障前的可观察顺序。

## 5. `0x00403F43` 遇敌门

普通世界尾部按以下顺序执行：

1. 查询 `sub_40DC50(ArgList + 0x1770)`；非零直接到公共尾部。
2. 递增 `dword_4C9A20`，32 位自然回绕。
3. 活动战斗 `dword_4CAEB4 != 0` 时退出。
4. 查询内部位 `0x0C`；零时退出。
5. 临时战斗请求 `dword_4A94AC != 0` 时退出。
6. Talk `source_guid != 0xFFFF` 时退出。
7. 调用 `sub_40DA60(counter, 0)`，并无条件把返回值写入临时请求。

因此只有第一个抑制门位于计数递增之前；活动战斗、位 12、已有请求和活动 Talk 都不会
阻止本帧计数增加。所有出口最终都在 `0x0040406F` 清零临时战斗请求，包括“入口时本来
就已有请求”的分支。

## 6. 非零战斗编号的立即切入

选择出非零编号后，原调用顺序为：

```text
0x00485710  停止旧 stream
0x00485740  停止全部 sample
0x00433010  释放切战斗前资源 A
0x00431960  释放切战斗前资源 B
0x00451B10  以低 16 位建立战斗
```

随后写活动战斗为一，按地址顺序清零 `0x004B7920`、`0x004B7518`、
`0x004A948C`、`0x004A9488`。地图 view 关闭成功时才把 `lpBaseAddress` 清零；失败时
报告诊断并保留地址。无论 view 关闭成功与否都继续关闭映射 handle 对象。

最后从角色索引一开始清除每条角色 `flags` 的 `0x01000000`，角色零明确不处理，再进入
公共尾部清临时请求。现代协调器用窄端口保留相同调用次序，并把 view 关闭失败作为结果
暴露。
