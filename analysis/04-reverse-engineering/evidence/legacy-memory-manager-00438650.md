# `0x00438650` 全局调试内存管理器

状态：`assembly_exact`；Windows LLVM 实现与进程生命周期已验证；原程序动态差分为 `blocked_runtime_oracle`

## 1. 边界与生命周期

本单元严格覆盖 `0x00438650..0x004389C4`：

- `0x00438650`：构造全局内存管理器；
- `0x004386E0`：由 `atexit` 包装器调用的析构主体；
- `0x00438800`：创建并清零 16 字节节点；
- `0x00438840`：释放节点；
- `0x00438880`：检查并释放节点持有的带哨兵内存块；
- `0x004389A0`：把 `GetLastError()` 格式化到对象错误缓冲。

`0x004389D0` 已有来自 `0x00448EE0` 和 `0x004490C0` 的直接业务调用，内部使用 `CharNextA` 处理有界字符串；它是另一套 DBCS 文本缓冲对象，不属于本单元。

`.CRT` 初始化入口 `0x00401000` 经折叠包装器对 `0x004B6C78` 调用 `0x00438650`，随后在 `0x00401020` 注册 `0x00401030`；后者把同一地址放入 `ECX` 并跳到 `0x004386E0`。因此该对象在主入口前创建，并在正常进程退出的 `atexit` 阶段销毁。

## 2. 对象与节点布局

全局对象从 `0x004B6C78` 开始，最后使用的错误缓冲为 `+0x224..+0x623`，对象末端恰为 `0x004B729C`。

| 偏移 | 宽度 | 汇编含义 |
| --- | ---: | --- |
| `+0x000` | 4 | `HeapCreate` 返回的私有堆句柄 |
| `+0x004` | 4 | 构造时清零；本单元内不再读取 |
| `+0x008` | 4 | 当前节点所持 payload 字节总数 |
| `+0x00C` | 4 | 历史节点数峰值 |
| `+0x010` | 4 | 当前已创建节点数 |
| `+0x014+i*0x10` | 4 | 32 个桶的辅助字段，构造时清零 |
| `+0x020+i*0x10` | 4 | 32 个活动节点链表头 |
| `+0x220` | 4 | 空闲节点链表头 |
| `+0x224` | `0x400` | 错误/报告文本缓冲 |

每个节点固定为 16 字节：`+0` 为内存块基址，`+4` 为 payload 长度，`+8` 为本单元未解释字段，`+0x0C` 为下一节点。跨平台 C++ 使用宿主指针宽度表达所有权，不承诺复制 x86 指针的物理宽度。

IDA 在 `0x004B6C8B` 标出了 `byte_4B6C8B[0x611]`，但六个代码引用均只把该地址作为前一组 72 个、步长 `0x21C` 记录的循环上界进行比较。实际记录区在 `0x004B6C70` 结束；`0x004B6C8B` 是“下一记录同字段”的常量地址，没有任何读写，不与本对象形成共享状态。

## 3. 构造与正常可达状态

`0x00438650` 依次执行：

1. `GetSystemInfo` 取得页大小；
2. `HeapCreate(HEAP_NO_SERIALIZE, page_size, 0)`，返回值直接保存，不检查失败；
3. 清零四个计数、32 个桶辅助字段和 32 个活动链表头；
4. 调用 `0x00438800` 共 32 次，把节点逐个压入 `+0x220` 空闲链表。

`0x00438800` 调用 CRT `malloc(0x10)`，但在判断返回值前已经向返回地址写入四个零 DWORD。分配失败会先发生空指针写访问异常，外层的 `"MemMgrObject node Create Failed"` 消息分支在正常受保护零页系统上不可达。每次成功创建都会递增当前节点数，并在需要时更新峰值。

完整汇编中：

- 全局对象地址只有构造和析构包装器引用；
- `0x00438800` 只由构造函数调用；
- `0x00438840`、`0x00438880` 和 `0x004389A0` 只在本对象析构链内互相调用；
- 没有函数向 32 个活动桶写入节点，也没有函数为节点建立带哨兵内存块。

所以当前链接二进制唯一正常可达状态是：私有堆已经创建，空闲链表含 32 个空节点，当前节点数与峰值均为 32，payload 总数为零，32 个活动桶全空。

## 4. 析构与异常分支

`0x004386E0` 先按 16 字节步长清空 32 个活动链表。每个活动节点都会报告 `"Resource not release ,Size[%d]"`，调用 `0x00438880` 释放其内存块，再移入空闲链表。随后逐个摘除空闲节点并调用 `0x00438840`，最后要求当前节点计数为零并调用 `HeapDestroy`。

`0x00438880` 的合同为：

- 空节点指针：写入 `"Internal error : NodeContainFree"` 并返回假；
- 节点没有内存块：不改节点并返回真；
- 节点有内存块：要求块首两个 DWORD，以及 `block + payload_size + 8` 处两个 DWORD，均为 `0xABCDDCBA`；
- 任一哨兵错误：报告 payload 地址、长度和前 16 字节并返回假；
- 无论哨兵是否正确，都会释放内存块、从 `+8` 总数减去 payload 长度，并清零节点四个字段。

`0x00438840` 只有在 `0x00438880` 返回真时才释放节点并递减当前节点数。当前二进制没有建立活动节点或带哨兵块的入口，因此泄漏、覆盖与节点不匹配报告只可能由对象外内存破坏触发；实现仍保留这些析构规则，但不虚构原程序不存在的公共分配 API。

## 5. 实现和验证合同

实现使用 `LegacyMemoryManager` 独立表达该全局调试对象：

- Windows 后端仍调用 `GetSystemInfo`、`HeapCreate(HEAP_NO_SERIALIZE, ...)`、`HeapDestroy` 和 `FormatMessageA`；
- 非 Windows 后端只替换未被任何节点使用的私有堆句柄，32 节点、计数、链表和析构顺序保持一致；
- 节点仍由 CRT `malloc/free` 路径单独管理，不从私有堆分配；
- 节点分配失败用确定性进程终止表达原汇编的空地址写崩溃，不把它修复成可恢复错误；
- SDL 应用在主入口前建立一个进程级实例，核心测试可显式建立独立实例。

固定 UT：

- 构造后私有堆可用、当前节点数 32、峰值 32、空闲节点 32、活动节点 0、payload 总数 0；
- 32 个桶的辅助字段与链表头均为零；
- 错误缓冲初始为空且容量保持 `0x400`；
- 连续构造和析构多个实例，验证正常可达生命周期没有计数、双重释放或销毁错误。

覆盖写、泄漏和空节点报告没有当前二进制的合法生产入口，以逐基本块静态映射保存；没有为测试增加原程序不存在的业务分配接口。

## 6. 逐地址实现映射

| 汇编地址 | C++ 映射 | 复核结果 |
| --- | --- | --- |
| `.CRT 0x00401000/0x00401020/0x00401030` | `src/platform/sdl3/main.cpp` 的进程级 `LegacyMemoryManager` | 主入口前构造，正常退出后由 C++ 静态析构调用 |
| `0x00438650..0x004386D7` | `LegacyMemoryManager::LegacyMemoryManager` | 页大小、无序列化私有堆、四个计数、32 桶和 32 次头插顺序一致 |
| `0x004386E0..0x004387F2` | `LegacyMemoryManager::~LegacyMemoryManager` | 活动桶报告/回收、空闲节点释放、计数检查和最后销毁私有堆的顺序一致 |
| `0x00438800..0x00438834` | `create_node` | 独立 CRT 分配、四字段清零、当前计数和有符号正常域峰值更新一致；失败保持终止语义 |
| `0x00438840..0x00438878` | `release_node` | 空节点直接失败；contained-free 失败时不释放节点；成功后才递减计数 |
| `0x00438880..0x0043899B` | `release_contained_block` | 空节点文本、四哨兵短路、覆盖报告、无条件释放 block、32 位字节计数减法和四字段清零一致 |
| `0x004389A0..0x004389C4` | `set_system_error` | Windows 继续以 `FORMAT_MESSAGE_FROM_SYSTEM`、当前错误码和 `0x400` 缓冲调用 `FormatMessageA` |

原节点是 16 字节 x86 结构；64 位重写的节点使用宿主指针宽度，因此节点本身的宿主分配尺寸不同。这是仅存在于不可见调试对象内部的 `platform_adapted` 表示差异；节点数、链表次序、计数和析构行为不变。非 Windows 私有堆同样属于平台适配，并且与原程序一样从不承担节点或 payload 分配。

## 7. 验证结果

- Windows LLVM `core-debug`：构建通过，27/27 CTest 通过。
- Windows LLVM `app-debug`：静态 SDL3 应用链接通过，27/27 CTest 通过，生成 `openswd3.exe`。
- `resource_io.legacy_memory_manager` 连续四次建立/销毁独立实例；每次均得到私有堆可用、32 当前节点、32 峰值节点、32 空闲节点、0 活动节点、0 payload、桶字段全零和空错误缓冲。
- 真实进程从 `build/runtime-smoke/launch` 启动，通过 `--data-dir E:\Game\swd3` 建立标题为 `OpenSWD3` 的窗口；正常关闭请求返回真，进程退出码为零。该路径实际覆盖进程级实例的主入口前构造和退出析构。

当前没有可运行的原程序内存状态捕获后端，不能把以上静态复核、UT 和新程序 smoke 升级为 `original_diff_verified`；该项继续标记 `blocked_runtime_oracle`。
