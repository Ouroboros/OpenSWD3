# 呈现、暂停与生命周期汇编证据

状态：P1.7 已从原 EXE 汇编交叉复核；完整 Blt/帧缓冲清单已由 P4 复核

来源：`swd3.exe`

SHA-256：`0bac897a7557735b22607d8c8f0a79a3e7ae7729deb56593fd91c21e10baee0c`

本证据覆盖：

- 画面最终送入 DirectDraw surface 的实际位置。
- `0x0040CF10` 的真实职责。
- F8 暂停与暂停画面。
- 窗口停用、最小化和恢复。
- 关闭请求、`WM_CLOSE`、`WM_DESTROY`、`WM_QUIT` 与 `WinMain` 返回。
- P1 控制流已经暴露的程序级错误出口。

## 1. 重要修正：0x0040CF10 不是画面呈现

`0x0040CF10` 的完整函数体只有四次对象调用：

```text
0x0040CF10  ECX = 0x004BA6E8 → 0x004854B0
0x0040CF1A  ECX = 0x004C9288 → 0x00486900
0x0040CF24  ECX = 0x004B7EB8 → 0x00485180
0x0040CF2E  ECX = 0x004C8450 → 0x00486080
0x0040CF38  AL = 1
0x0040CF3A  return
```

下游汇编确认：

- `0x004854B0` 维护排队的音乐/流切换状态，并调用 Miles 流或 sequence 相关对象。
- `0x00486900` 轮询 `AIL_stream_status`，调整流音量，并关闭、释放已经结束的 stream。
- `0x00485180` 轮询 `AIL_sequence_status`，调整 sequence 音量，并结束、释放已经完成的 sequence。
- `0x00486080` 轮询 `AIL_sample_status`，结束已经完成的 sample，并维护样本内存引用。

所以 `0x0040CF10` 的已确认语义是“集中维护 Miles 音频对象”。

它在 `0x0040A570` 的结构上位于多个分支的公共尾部，但不能命名为 `Present`、`Flip` 或“最终呈现”。

## 2. 原程序没有单一的最终呈现函数

DirectDraw surface 的 `Blt` 由虚表偏移 `+0x14` 调用。完整汇编中共有 32 个此类调用，其中 21 个写向 primary surface。P1 最初列出的以下 7 个地址是顶层稳态画面分支的典型提交，不是完整清单：

- 普通世界：`0x004120B0` 内的 `0x00412716`。
- 战斗：`0x00453200` 内的 `0x0045350A`。
- 特殊模式一、三至六：`0x00439FD0` 调用 `0x0043A610`，在 `0x0043A854` 呈现。
- 特殊模式二：`0x0044EA60` 内的 `0x0044F765`。
- F8 暂停画面：`0x00411FA0` 内的 `0x00412046`。
- Bink 视频：`0x00484950` 内的 `0x00484A11`。
- 高优先级画面：`0x00406E30` 下游 `0x00408CF0` 内的 `0x00408D5E`。

这 7 个调用都先通过 `0x00437DF0(0x2711)` 取得目标显示 surface，并把 `0x004ACBA0` 作为源 surface。其余 14 个主画面提交分布在存取档 UI、媒体检查、剧情 VM、场景清屏和战斗转场；其中还有两个动态矩形战斗位移、从战斗快照/临时 surface 向 primary 的提交，不能统一概括为 `0x004ACBA0` 的整 surface Blt。

已经确认的参数差异：

- 普通世界、特殊模式一/三至六、高优先级画面使用 `0x01000000` 标志。
- 战斗、特殊模式二和暂停使用零标志。
- 视频把同一局部矩形 `{0,0,639,479}` 同时作为源、目标 RECT，使用 `0x01000000`，并对多个 `DDERR_*` 返回值分别处理。

完整 21 个调用中，18 个使用 NULL source/destination RECT，两个使用动态战斗位移矩形，一个使用上述 Bink 固定矩形；9 个使用 `0x01000000`，12 个使用零 flags。除 Bink 外，正常主画面提交不根据 HRESULT 改变后续逻辑。逐地址清单和帧地址生命周期见 `framebuffer-and-display-presentation.md` 与 `../inventory/primary-presentation-paths.tsv`。

因此顶层顺序不是：

```text
更新所有游戏系统 → 单一 Present
```

而是：

```text
选择互斥画面分支
  → 该分支内部更新、软件绘制并 Blt
  → 部分路径再执行 0x0040CF10 音频维护
  → 检查程序关闭请求
```

重写可以把平台输出统一为一个现代 `present()` 接口，但兼容层必须保留每条原分支何时完成软件画面、何时呈现、何时维护音频的顺序。

## 3. 0x00437AE0 只服务显示恢复路径

`0x00437AE0` 只有 `0x0040AB50` 的恢复循环调用。

它根据图形对象 `+0x34` 的位零分为两条路径：

- 该位为一：检查 surface 丢失状态，必要时调用虚表 `+0x6C` 恢复，再通过虚表 `+0x2C` 执行 Flip。
- 该位为零：通过虚表 `+0x14` 重试 Blt；遇到 `0x887601C2` 时恢复两个 surface 后继续重试。

所以它是显示恢复/重新绑定阶段的 Blt 或 Flip 重建循环，不是普通每帧共同调用的最终呈现入口。

## 4. F8 暂停路径

窗口过程的 `WM_KEYUP` 在 `wParam == 0x77` 时处理 F8：

- 视频活动位 `[0x004B7A9C] & 0x20` 非零时，把 `[0x004CC2AC]` 强制写一。
- 其他情况下，在零和一之间切换 `[0x004CC2AC]`。

`WinMain` 的无消息路径随后按该值分派：

```text
[0x004CC2AC] != 0 → 正常视频/帧/门控路径
[0x004CC2AC] == 0
  ├─ [0x004B7CAC] == 1 → 0x00411FA0
  └─ 其他 → Sleep(0)
```

`0x00411FA0` 每次被调用都会：

1. 分配 64 字节并复制 Big5 文本“遊戲暫停  按F8繼續遊戲”。
2. 计算居中位置并把提示绘入软件帧缓冲。
3. 释放临时字符串。
4. 在 `0x00412046` 直接调用 DirectDraw `Blt`。

暂停时不会进入 `0x0040A570`，因此不执行正常输入采样、时钟迁移、世界、剧情或战斗更新。暂停提示不是一次性画面，而是在消息队列为空且窗口处于恢复状态时反复呈现。

## 5. 窗口停用、最小化和恢复

窗口过程把以下消息交给 `0x0040AB50`：

- `WM_SIZE`：`wParam` 为一、三、四时调用 `0x0040AB50(0)`；为零、二时调用 `0x0040AB50(1)`。
- `WM_ACTIVATEAPP`：`wParam == 0` 时调用零参数路径，非零时调用一参数路径。
- `WM_SYSKEYDOWN` 的低字节为 Enter 且内部门控允许时，根据 `[0x004B7CAC]` 在两条路径间切换。

### 0x0040AB50(0)

停用路径的已确认顺序：

1. 确认显示 surface 已存在，把当前帧间隔压栈后调用 `0x0040DD30`；该 helper 不读取栈值，只把全局 interval 清零，随后旧值被丢弃。
2. 调用 `0x00485710`、`0x00485740` 和 `0x0040CF10` 处理音频停用与对象维护。
3. 战斗活动时调用 `0x00451AE0`。
4. 对 `0x004AB998`、`0x004C9A28`、`0x004A9ED0` 三个字体 renderer 调用 `0x004351F0`，释放其 HFONT、临时 surface、字形缓存和相关内存。
5. 写 `[0x004B7CAC] = 0`、`[0x004BABA4] = 1`。
6. `ShowWindow(hWnd, 6)` 后返回零。

### 0x0040AB50(1)

恢复路径的已确认顺序：

1. `ShowWindow(hWnd, 9)`。
2. `SetWindowPos` 把窗口放到 `(0, 0)`，大小固定为 `640×480`。
3. 写 `[0x004B7CAC] = 1`。
4. 对目标 surface 和 `0x004ACBA0` 调用虚表 `+0x6C` 恢复，再调用 `0x00416D30` 重建关联状态。
5. 通过 `0x0040F340` 按 20、16、12 三种字号重新建立三个字体 renderer。
6. 写 `[0x004BABA4] = 0`。
7. 战斗活动时调用 `0x00451A90`。
8. 循环查询显示 surface；不匹配时调用 `0x00437AE0`，直到目标 surface 一致。
9. 调用 `0x0040DD20(0x23)` 后返回零。

这套逻辑是 DirectDraw surface 丢失、旧式独占/窗口状态和 GDI 字体 surface 重建的兼容负担。完整 `sub_40AB50` 没有调用 DirectInput wrapper，也没有重新 Acquire/初始化输入设备；此前把三个 `sub_4351F0/sub_40F340` 对象写成输入对象是错误归类，现已按汇编和字体对象字段纠正。SDL3 重写不需要逐 API 仿制，但必须恢复对游戏可见的状态：停用期间不更新正常帧，恢复后字体、战斗画面和呈现对象在同样的边界重新可用。

## 6. 关闭生命周期

### 延迟关闭请求

多个子系统通过：

```text
[0x004B7A9C] |= 0x04
```

提出程序级关闭请求。

`0x0040A570` 的未提前返回路径在 `0x0040AB13` 检查该位。非零时同步调用：

```text
SendMessageA(hWnd, WM_CLOSE, 0, 0)
```

窗口过程没有专门消费 `WM_CLOSE`，因此消息落到 `DefWindowProcA`。默认处理销毁窗口并产生 `WM_DESTROY`。

### WM_DESTROY

`0x0040A1FA` 的顺序是：

1. 查询内部位编号一。
2. 若该位非零，或 `[0x004B7A9C] & 0x04` 非零，调用 `0x004251B0` 完整释放路径。
3. 无论是否执行完整释放，都调用 `CoUninitialize`。
4. 调用 `PostQuitMessage(0)`。
5. 随后仍进入 `DefWindowProcA`。

### WM_QUIT 与 WinMain 返回

`PostQuitMessage(0)` 使下一次 `GetMessageA` 返回零。`WinMain` 读取 `msg.wParam` 并返回，CRT 再把该值交给 `_exit`。

原汇编只区分 `GetMessageA == 0` 和非零。`-1` 会被当作普通非零结果，继续传给 `TranslateMessage` 和 `DispatchMessageA`。这是原程序的实际错误边界。

## 7. 直接销毁与错误出口分类

P1 已确认两类程序退出触发方式。

第一类是直接同步发送 `WM_DESTROY`：

- 启动对话框返回六。
- DirectDraw 初始化失败：`0x00424FBB` 起先设置关闭位、显示 `DDraw init Failed.`，再发送 `WM_DESTROY`。
- 地图载入的结构条件失败：`0x00425ED2` 起设置关闭位并发送 `WM_DESTROY`。
- Talk 文件无法打开的剧情载入路径。

第二类只设置关闭位，等待可到达的主帧尾转换为 `WM_CLOSE`：

- 普通世界路径 `0x0040313A`。
- 选择/载入路径 `0x00411C78`，并返回二。
- 地图编号查找失败 `0x00425DA0`。
- 剧情 VM 致命出口 `0x0042D4B6`，并返回零。
- 特殊模式分派 `0x00449320`。
- 视频选择/打开路径 `0x0048477D`，并返回零。

这些地址只证明“请求退出”的机器级结果。除已有错误字符串的分支外，P1 不为其猜测更具体的用户业务名称。

还存在返回失败但只终止当前子系统的路径。例如战斗操作码三十一的边界错误返回零会结束战斗结果链，不等价于直接关闭整个程序。

## 8. P1.7 对重写规格的约束

- 不把 `0x0040CF10` 翻译成渲染或呈现接口。
- 音频 stream、sequence、sample 的状态轮询属于原帧时序的一部分。
- 每个顶层画面模式都有自己的软件绘制和呈现边界。
- 暂停冻结正常游戏帧，但仍反复绘制并呈现暂停提示。
- 失焦期间抑制正常帧；恢复动作对输入、图形和战斗状态具有可见顺序。
- 关闭既有延迟标志路径，也有直接 `WM_DESTROY` 路径。
- 新程序可以用 SDL3 事件和现代纹理替代 DirectDraw/DirectInput，但兼容测试必须覆盖上述状态迁移和调用顺序。
