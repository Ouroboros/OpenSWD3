# LMF 世界地图会话组合：0x00425BE0

状态：LMF 子链、CM 插槽、地图业务对象与渲染源生命周期 `assembly_exact`、`asset_verified`

来源：`swd3.exe.lst` 完整汇编。汇编是唯一行为真值。

## 当前实现边界

`LegacyWorldMapSession` 把 B2 已验证的物理读取器按 `0x00425BE0` 中的原顺序组合。
地图头和地表流之间不是无缝连接，完整外部数据顺序为：

```text
尾索引查找地图号
→ 固定头与名称
→ pre-surface 插槽：0x00426044 调用 sub_426840 取得或生成 CM
→ 地表原样表和压缩格
→ 地表后变长记录
→ 相对引用目录
→ 头 +0x14 目录
→ 头 +0x18 索引对象及解压负载
→ 头 +0x1C 目录
```

每一步只在前一步成功后执行，首个失败立即保留为明确阶段状态。地图号仍以完整 `u32`
进入尾索引查找，后续全部读取统一使用查找得到的地图块偏移。

`0x00425F68` 的 `sub_411620` 不是 CM：它按地图高度释放、重建并清零三块空间工作区。
真正的 CM 调用位于 `0x00426044`，目标 `sub_426840`，返回值写入地图状态 `+0x20`；
随后 `0x0042606B` 才重新定位 LMF，`0x00426097` 开始读取地表原样表。不得把
`sub_411620` 错标为缓存加载器。

`sub_426840` 最终进入 `0x00426840` 取得或生成 CM 映射；该部分已由
[`cm-cache-runtime-00426840-004272b8.md`](cm-cache-runtime-00426840-004272b8.md) 闭环。
物理目录后的事件、两种角色记录、三组空间链和受检格索引由
[`lmf-map-business-004261ce-00426798.md`](lmf-map-business-004261ce-00426798.md) 闭环。

## 现代边界

资源层继续拥有文件、压缩流和物理目录解析；世界模块拥有一次地图装载的组合顺序和会话
生命周期。`LegacyWorldMapPreSurfaceStage` 固定头后、地表前的外部插槽；
`LegacyWorldRenderSession` 在该插槽生成/命中 CM，并共同拥有 LMF 会话、CM 字节及 8 位
地图调色板。其 `background_source()` 只借用这些拥有型容器，不产生悬空的原全局裸指针。

实际程序缓存目录由调用者显式传入；平台层将使用 OpenSWD3 自有缓存目录，不改写原游戏
`Data`。这是存储位置适配，不改变 CM 内容、命中/淘汰算法或地图逻辑。目录无法建立、CM
失败和损坏资源均保持明确状态；成功资产不会重排或合并物理读取阶段。

## 8 位地图的 0x200 字节调色板

地图加载调用者在 `0x0040C6F3` 检查像素位数。恰为 8 时：

1. `0x0040C6FC` 分配 `0x200` 字节；
2. `0x0040C706..0x0040C718` 从 CM 映射起始地址复制 128 个 dword；
3. `0x0040C720..0x0040C726` 对这 256 个 `u16` RGB555 项调用 forward 转换；
4. `0x00412A42..0x00412A47` 在 8 位底图绘制期间把该缓冲区作为 palette；
5. tile index 数据则从同一 CM 的 `0x200 + tile_index * 0x100` 开始。

因此 8 位 palette 不是未知外部文件，也不能伪造；它就是 CM 的首 `0x200` 字节。现代
会话把这 256 项解成小端 `u16` 并执行同一个无舍入 forward 转换，CM 原字节仍原样拥有。

## 验证

合成端口 UT 覆盖八阶段严格顺序、CM 严格位于 header 与 surface 之间、统一地图偏移、
每个阶段的首次失败短路、8 位 palette 拥有/转换、短 palette 与非 8/16 位显式失败。真实
`huge.lmf` 固定验证地图 22、24、500：三张均完成全部 LMF 子链；偏移、尺寸、地表输出
大小和尾随记录数与库存一致；地图 22/24/500 的业务角色数固定为 49/29/1，格索引
全部合法。统一渲染会话另固定地图 24 的 RGB565 全屏哈希
`0x947C15A53487BF9A`，以及 8 位地图 4 的 CM palette + tile 全屏哈希
`0xF00691829E9FE2D5`。Linux `core` 135/135、Windows LLVM `app` 139/139 CTest
全部通过。
