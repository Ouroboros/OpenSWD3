# TSW 图像资源包、帧描述符、主压缩流与未消费辅助载荷规格

最后更新：2026-10-01

状态：六个样本的 18,000 个物理索引槽、2,928 个非空块、20,091 帧、全部主压缩流及运行时辅助指针合同已验证

来源：`swd3.exe` 完整汇编与工作区六个 `all_*.tsw` 样本

完整汇编是唯一真实依据。IDA 伪码只辅助定位。

## 总结

TSW 是按资源编号直接定位的图像/精灵资源包。六个文件各保留 3000 个、每个 44 字节的物理索引槽：

| 资源编号商 | 文件 |
|---:|---|
| `0` | `all_char.tsw` |
| `1` | `all_item.tsw` |
| `2` | `all_magic.tsw` |
| `3` | `all_sys.tsw` |
| `4` | `all_map1.tsw` |
| `5` | `all_map2.tsw` |

运行时使用：

```text
group          = resource_id / 3000
record_number  = resource_id % 3000
index_offset   = record_number * 44 - 16
               = 0x1C + (record_number - 1) * 0x2C
```

`0x00431C50–0x00431D85` 完成分组和余数运算，`0x00433380–0x0043348B` 按上述公式读取索引。运行时不会先用文件头 `+0x18` 的数值限制 `record_number`。

这一点不是理论推断：`all_map2.tsw` 的头部声明值是 82，但物理槽 1000 存在非空资源 ID 16000，名称为“大鐘”，包含一帧 24 位、212×160 的资源。按头部值截断会丢失原程序可直接访问的真实资源。

## 文件头与固定索引

| 文件偏移 | 宽度 | 当前结论 |
|---:|---:|---|
| `+0x00` | `0x18` | 六个样本均为零；运行时不读取 |
| `+0x18` | 4 | 声明记录数；不是物理索引边界，也不是可靠的最高非空槽 |
| `+0x1C` | `3000 × 44` | 固定物理索引区 |
| `+0x203BC` | — | 固定索引区末端；最早资源块可以从这里开始 |

`0x00431A50` 从 `0x1C` 开始连续读取 `0x203A0 = 3000 × 44` 字节，独立证明 3000 槽是物理布局而非样本猜测。

六个样本共有 18,000 个物理槽、2,928 个非空槽。头部声明数合计 2,937，但其中含 10 个空槽，同时漏掉 `all_map2.tsw` 的槽 1000。

## 44 字节索引记录

| 记录偏移 | 宽度 | 当前结论 |
|---:|---:|---|
| `+0x00` | 20 | 名称字节区；运行时查找不读取 |
| `+0x14` | 4 | 整个资源块长度 |
| `+0x18` | 4 | 资源块绝对文件偏移 |
| `+0x1C` | 4 | 存储元数据编号；当前非空样本都等于物理槽序号 |
| `+0x20` | 4 | 当前样本为零，运行时主加载路径不读取 |
| `+0x24` | 4 | 当前样本为零，运行时主加载路径不读取 |
| `+0x28` | 4 | 当前样本为零，运行时主加载路径不读取 |

资源选择必须按编号的商和余数直接定位，不能改成按名称或 `+0x1C` 搜索。

## 资源块头

索引 `+0x18` 指向 12 字节块头：

| 块偏移 | 宽度 | 当前结论 |
|---:|---:|---|
| `+0x00` | 4 | 活跃值，最终语义未知 |
| `+0x04` | 2 | 固定魔数 `0xABCD`；`0x004332C4` 精确比较 |
| `+0x06` | 2 | 帧/变体数量 |
| `+0x08` | 2 | 存储位数；样本出现 8、16、24 |
| `+0x0A` | 2 | 固定值 12，与块头尺寸一致 |

只有 `+0x08 == 8` 时，`0x004332E7–0x00433305` 在块头后读取 512 字节调色板。16 位和 24 位记录不走调色板读取。

样本记录分布为 1638 个 8 位块、1281 个 16 位块和 9 个 24 位块。不能把 TSW 固定成单一 16 位格式。

## 36 字节帧描述符

描述符表位于：

```text
block + 12 + (storage_bpp == 8 ? 512 : 0)
```

每帧 36 字节：

| 描述符偏移 | 宽度 | 当前结论 |
|---:|---:|---|
| `+0x00` | 4 | 主压缩流相对块起点的偏移 |
| `+0x04` | 4 | 主压缩流长度 |
| `+0x08` | 4 | 主流声明解压长度 |
| `+0x0C` | 4 | 辅助组存在标记/元数据；当前加载器只测试是否非零，未把数值当偏移或长度消费 |
| `+0x10` | 4 | 主流后物理辅助载荷跨度；当前两套加载器均不读取 |
| `+0x14` | 4 | 辅助平面名义像素数；非零的 7316 帧全部严格等于 `width × height` |
| `+0x18` | 4 | 辅助组类型/编码候选；样本出现 0、1、2，当前 EXE 加载器不读取 |
| `+0x1C` | 4 | 当前 20,091 帧全部为零；当前加载器不读取 |
| `+0x20` | 2 | 宽度 |
| `+0x22` | 2 | 高度 |

全部样本满足：

```text
next_primary_offset = primary_offset + primary_compressed_size + field_10
final_block_size     = last_primary_offset + last_primary_size + last_field_10
```

20,091 帧中有 7316 帧同时满足 `+0x0C != 0` 且 `+0x14 == width × height`，其中 7148 帧的 `+0x10` 非零，物理辅助载荷合计 8,463,829 字节。它们只出现在 7312 个 16 位帧和 4 个 24 位帧；非零 `+0x10` 则全部属于 16 位帧。这组关系足以证明它不是任意块间填充，但在没有消费汇编前仍只命名为“辅助组/辅助载荷”，不擅自断言是 alpha、coverage 或某种压缩格式。

当前 EXE 的两套加载器 `0x00433540` 与 `0x004338F0` 都只读取并解压 `+0x00/+0x04/+0x08` 指定的主流。它们只把 `+0x0C` 当布尔条件，并在非零时把临时返回记录 `+0x08` 写成零；`+0x10/+0x14/+0x18/+0x1C` 完全不被这两函数读取。也就是说，磁盘上存在辅助载荷不等于当前 EXE 会把它接入绘制器。

原程序按请求变体直接读取第 `variant + 1` 份描述符数据，没有在 `0x00433540` 内再次比较块头帧数。重写不能偷偷加入会改变有效调用行为的变体钳制；安全检查只能作为不影响有效输入的兼容/诊断层。

## 主压缩流与 `0x004399E0`

`0x004335E4–0x00433670` 和 `0x0043397A–0x004339F5` 都执行相同顺序：

1. 按描述符 `+0x04` 读取主压缩流。
2. 按 `+0x08` 分配目标缓冲区。
3. 调用 `0x004399E0`。
4. 要求实际输出长度严格等于声明长度。

验证器按完整汇编的 token 分支、回溯距离、结束标记和输入恰好消费规则重现有效流行为。六个样本结果：

- 20,091 帧全部成功。
- 558,351,505 字节主压缩输入全部恰好消费。
- 实际输出合计 1,378,998,573 字节，逐帧与声明长度完全一致。
- 没有一帧依赖忽略尾部输入或容忍长度不匹配。

这证明当前 TSW 主流与恢复出的 `0x004399E0` 有效流算法完全匹配。进一步的全量首字分类证明 20,091 条解压主流全部以小端 `0xFFFF` 开始；在 `0x004CD764 == 0` 的普通世界绘制环境中，它们全部选择软件 blitter 的低位 RLE/span 函数族，没有当前 TSW 主流落入原始矩形 `+0x80` 族。

该结论仍不能单独证明原函数与某个现代 LZO 库在损坏输入、越界输入和错误码上 100% 等价；替换库之前仍需逐分支比较错误约定。

解压输出不是可直接按 `width × height × bpp` 解释的原始像素平面。它会继续交给 `0x004170E0` 等精灵绘制函数解析；因此现阶段命名为“解压后的精灵命令流/图像流”，不擅自输出 PNG 或改成普通 RGBA 位图。

## 运行时返回记录

`0x00433380` 最终向调用方填充至少 20 字节记录：

| 偏移 | 宽度 | 当前结论 |
|---:|---:|---|
| `+0x00` | 4 | 解压后主流指针 |
| `+0x04` | 4 | 当前两套加载路径恒为零；由零初始化临时记录 `+0x08` 复制而来，不指向磁盘辅助载荷 |
| `+0x08` | 4 | 8 位块调色板指针；非 8 位路径为零 |
| `+0x0C` | 2 | 宽度 |
| `+0x0E` | 2 | 高度 |
| `+0x10` | 4 | 解压后主流字节数 |

`0x00433383–0x00433395` 与 `0x00433723–0x00433735` 都先把六个临时双字清零；公共返回段再分别于 `0x0043351A–0x00433526` 和 `0x004338A5–0x004338AD` 把临时 `+0x08` 复制到运行时 `+0x04`。低层函数对临时 `+0x08` 的唯一写入又都是零。因此这不是“样本通常为空”，而是当前汇编加载合同恒为零。`0x00401E42` 的 8 位源转换只清运行时 `+0x08` 调色板槽，不会生产或改变 `+0x04`。

缓存节点由 `0x00431C81–0x00431CEA` 分配 32 字节：前 8 字节保存 16 位资源编号、16 位变体和 next 指针，返回记录从节点 `+0x08` 开始。缓存按资源编号十取余分桶，命中时移到桶首。

## 运行时查询与十桶缓存

`0x004315D0` 在第一次缓存查询时一次性以 `FILE_SHARE_READ` 打开六个 TSW；此后的
逻辑查询把两个四字节栈槽分别截断为低 16 位。普通资源按 `resource_id / 3000` 选包，
按 `resource_id % 3000` 选物理记录；`resource_id == 0xFFFF` 不进入六包除法，而以
`variant_index % 10` 选桶并调用独立特殊图像加载路径。`0x00431A20` 只查已有缓存，
不会触发文件初始化或缺失帧装载。

外层缓存严格为 10 个单链表：普通资源按 `resource_id % 10` 分桶，特殊资源按
`variant_index % 10` 分桶。节点命中后移到桶首。总容量只累计节点运行时 `+0x10` 的
转换后主命令流长度；32 字节节点、调色板和辅助指针都不计入容量。

淘汰不是全局 LRU，且顺序不能按常见缓存实现改写：

1. `0x004315D0` 在查找是否命中之前，按signed32比较 `current_bytes >= limit`，
   成立就先调用 `0x00431EA0`。实际条件是 `0x00431723 JL` 的反侧，不能改成unsigned。
   限额的静态初值为 `0x00600000`（6 MiB）；`0x004315C0..0x004315C9` 的setter
   原样写入四字节参数，不钳制、清高位或解释为宿主size_t。
2. `0x00431EA0` 只在进入时选择一次节点数最多的桶；数量相同时保留编号较小的桶。
3. 此后连续删除该桶的尾节点，直到总字节按signed32低于上限或该桶计数减至零；
   `0x00431EDA JL` 和 `0x00431F76 JGE` 同样有符号。桶空后即使总字节仍高于上限，
   也不会重新选择第二个桶。初次选择已空桶时没有预先跳过尾部操作的指令，不能把
   宿主empty guard当成完整原版错误路径；异常释放、16位桶计数回绕仍需另行闭合。
4. 每次删除只减去主命令流长度，并按主流、辅助、调色板、节点的顺序释放所有权。

物理帧装载后，`0x00431DB1 -> 0x00401C70` 把 indexed8 命令流通过外置 256 色表
转换为 direct16，并释放外置调色板；非 indexed8 命令流也按当前 forward pixel
converter 处理。缓存容量因此统计转换后的长度，最终借用 view 的辅助流和 palette
均为空。现代实现对应 `LegacyTswArchive` 与 `LegacyTswRuntime`：保留上述键宽、查询
顺序、桶内 MRU/尾淘汰、特殊资源端口及共享读句柄；越界物理记录和六包表外组只在
宿主安全层返回显式错误，不改变有效资产路径。

现代查询结果新增 `frame_owner` 租约：`frame` 仍是借用的 span，
只有查询结果持有该 owner 时才能跨后续查询、淘汰或 `close()`
安全读取；单独复制 span 不携带租约。缓存淘汰和容量统计仍以
节点为准，租约保活的帧不计入缓存容量。这是宿主借用生命周期
边界，不声称原 EXE 淘汰后的旧指针仍可访问。特殊帧同桶淘汰
并重载后，旧查询结果仍保留旧字节与不同的 owner；关闭缓存后
旧结果也仍可读。增加对失败帧长度的测试防护后，最新
Linux core `199/199`（`proc_d479`）、ASan core `199/199`
（`proc_55d9`）、Linux app `205/205`（`proc_26e0`）通过。
该租约原先尚未接入战斗生产 lookup 端口。

为供工作包 316 的真实帧查询使用，缓存 miss 现在从
进程内 32 位虚拟地址区分别保留节点的 32 字节与
主命令流区域：记录 token 是节点 token `+8`，
与主流 token 不相等。分配游标跨多个 TSW 运行时
实例共享且单调递增，关闭缓存不回退；两份同时存活
的帧或清除后重新装载的帧不复用这两个地址。
这不是原版堆指针值，也不覆盖其他模块的地址
注册、非法指针行为或 `sub_4315D0` 的异常前缀。
命中时公开独立 LST 推得的 ECX/EDX：桶首
ECX 是低16位资源/变体组合键，非首 ECX 是
原桶首节点，EDX 是十桶头地址；新装载成功
ECX 是转换后主流长度，EDX 是新的容量字节总数。
缓存 metadata 的局部测试不能替代完整战斗调用链
或原版动态差分。独立 HEAD `b11c3407` 加本
TSW 三文件补丁与主工作树对应文件 SHA-256
逐一相同；隔离 Linux core `199/199`
（`proc_251d`）、ASan core `199/199`
（`proc_06df`）、Linux app `205/205`
（`proc_b760`）通过，结论只适用于该切片。

`0x00431A50/0x00431AA0` 为 `all_magic.tsw` 维护的五项描述符磁盘读取加速层不拥有
最终帧，也不改变外层十桶缓存、解压结果或借用 view。当前最小闭环直接从同一物理
描述符读取，后续 78 地址有限收口时把这两项登记为内部 I/O 优化映射，而不复制其
进程全局暂存布局。

### 加载之前发布节点，未知装载不撤销登记

`0x00431C93` 先增加桶计数；`0x00431CB6` 发布分配后的新头，
`0x00431CCE` 清零八个双字，再于 `0x00431CDD/0x00431CEA/0x00431CF4`
登记两个16位键与next。此后才调用特殊或普通图像加载器。
普通加载返回零时，`0x00431D91..0x00431DA6` 没有删除节点或恢复旧头；
外层 `0x0043174E` 只清结果全局。下一次同键的查找不检查图像是否有效。

B10工作包316据此修正宿主缓存：先保留32字节节点身份、发布键，再尝试装载。
节点与图像可用性分开；装载中及失败状态保留在节点上，重复查询仍命中原节点，
不因为图像不可用就重新装载。失败状态不是原版错误码或CPU现场。
非ready查询的`frame_owner`仅标识已登记的记录，`frame`不发布图像span；
其中默认字段不证明原版载荷全零。宿主节点在加载调用期间独立持有，
已完成图像仍以不可变租约借用，不把宿主保活等同于原版已释放地址有效。

实际战斗TSW端口对上述未知载荷的命中，仅返回由 `0x00431DF0/0x004315D0`
可推得的记录身份、ECX/EDX与TEST定义FLAGS，不宣告资源头或decoder source已知。
首次未知加载仍不伪作返回；失败后的完整栈/GPR/FLAGS与共享全局尚未恢复。
B10后续独立审查又修正现场报告：失败回复显式physical_state_known=false，
不以4315D0入口或默认零GPR充作已发生host查询后的物理现场。
父与共享caller只保留最后确认的checkpoint，停止地址0表示不可用而非guest fault；
正常返回/明确供应的首MOV停止保持原合同。六项冻结新快照 `proc_67cb` 192秒exit0，
定向1/1、core/ASan各200/200、app206/206通过，四日志诊断0，局部差分无跳过。
这只证明现场有效性处理，不是失败后CPU状态恢复或原版查帧动态差分。
淘汰碰到未知载荷时，在缺少 `0x00431F11` 长度及四次free输入处保留节点，
不把空的宿主vector大小当作原版零长度，不减容量或伪造释放。

独立加载观察、失败节点保留及真实端口反例先在旧生产源码上失败。
旧快照两个定向目标共三项新增断言失败，其余断言与编译无诊断。
新冻结快照 `proc_ff24` 391秒退出0：两个定向各1/1，
Linux core/ASan各200/200、app206/206通过，五日志诊断0、六项SHA匹配。
动作17组与seq372局部差分实际执行，无跳过，不是查帧原版动态差分。
空桶错误、16位计数回绕、DF=1物理写、递归改变缓存、首次失败ABI和完整CRT仍未闭合。

## 1:1 重写约束

- 每个 TSW 必须保留 3000 个物理索引槽；不得按头部声明数截断。
- 资源选择必须按 `/ 3000` 与 `% 3000` 直接定位；不得改成按名称或元数据 ID 搜索。
- 8 位块的 512 字节调色板条件读取必须保留，16/24 位块不得强行套同一布局。
- 36 字节描述符的全部字段和主流后的辅助载荷必须保留，即使当前 EXE 不读取；不得因为运行时 `+0x04` 恒零就从容器规格中删除这些磁盘字节。
- 主流解压必须要求输入恰好消费和输出长度精确匹配；不能静默接受截断或额外尾字节。
- 解压输出仍是原精灵/图像命令流，初步还原不得提前转换成会改变绘制和混合行为的现代位图语义。
- 当前行为兼容层不得自行解码辅助载荷并接到运行时 `+0x04`；那会激活原 EXE 当前资产路径没有启用的 `0x08` RLE coverage 行为。
