# 旧视频对象、帧服务与替换端口

最后更新：2026-08-09

状态：11 个 B5 视频地址已按完整 LST 实现为平台无关端口；实际 Bink 解码延期到统一 `libffmpeg` 动态库

完整 LST 是唯一行为真值。本文只描述 `0x00484550..0x00484DA0` 中游戏实际使用的
Bink 边界、活动对象状态和每帧顺序；Bink SDK 名称只用于说明旧外部调用，不进入新核心
接口。

## 1. 旧对象与打开/关闭

`0x00484550` 先按第二个参数低八位选择 `BinkOpenMiles` 或
`BinkOpenDirectSound`，再用 DirectDraw surface 调用 `BinkDDSurfaceType`，把返回值保存
到全局 `0x0053D06C`。这个值只供后续帧复制使用；唯一调用者不检查函数返回。

`0x00484590` 只把新对象前两个四字节清零。`0x004845A0` 的四个栈槽依次是文件名、
打开参数占位、音量和窗口句柄：

1. 文件名指针为空时直接返回零。
2. 以固定 flags 零打开文件，把句柄写入对象首字段；失败时复制外部错误字符串到
   `+0x84`。
3. 从 `+0x08` 起清零固定 `0x7C` 字节，再取得 summary。汇编在打开失败后仍会把空句柄
   传给 summary；这是原始危险路径，不把它误写成成功传播。
4. 音量为负时写零，否则只在大于 `0x8000` 时钳制；所有路径都返回零。

`0x00484620` 在首句柄非零时执行 close、清空首字段并返回一；句柄为空时返回零。
`0x00484920` 对全局活动对象执行相同关闭，再释放对象、清空 `0x0053D070` 并清除进程
位 `0x20`。

## 2. 帧门控与帧推进

`0x004846F0` 在句柄为空时返回零；否则把 `BinkWait` 任意非零值规范化成一。
`0x00484950` 遇到一便立即返回，本轮不 decode、copy、advance、service 或 present。

`0x00484650` 在非等待帧严格执行：

```text
decode
→ copy(destination, pitch, 480, centered_x, centered_y, surface_type)
→ 读取 handle+0x08 的总帧数
→ 读取 handle+0x0C 的当前帧号
→ 总帧数 > 当前帧号时 advance
→ service
```

copy 返回零时原程序先显示 `BinkCopyToBuffer Fial`，但仍继续帧号判断与 service。函数
初始结果是总帧数的 32 位回绕取负；只有无符号 `总帧数 > 当前帧号` 时才改回总帧数并
advance。`0x00484950` 随后提交固定 `{0,0,639,479}` 的 DirectDraw Blt，最后只在该有
符号结果小于等于零时关闭活动对象。因此终止帧仍先复制、service 和 present，再关闭。

`0x00484710` 与 `0x00484720` 读取的是播放器对象 summary 的宽和高，不是 Bink 句柄中
同偏移的帧字段。`0x00484950` 以有符号 `(640-width)/2` 和 `(480-height)/2` 居中，除法
按 x86/C++ 向零截断。

`0x00484DA0` 是脚本可见的进度查询：没有活动对象或句柄时返回 `-1`；否则先读当前
帧号、再读总帧数。当前帧号无符号小于等于总帧数时原样返回，超过时返回当前帧号的
32 位回绕取负。

## 3. 剧情播放请求

`0x00484730` 先调用 `0x004118B0` 取得媒体根；用户取消时设置关闭请求位 `0x04` 并返回
零。正常路径组成 `swd3\\video\\<脚本文本>`，把文件名中的 `.avi` 或 `.mpg` 原地改成
`.bik`，分配 `0x484` 字节播放器对象，按当前音量打开，然后无条件写全局活动对象、设置
进程视频位 `0x20` 并返回一。这里不因旧 `BinkOpen` 失败改变返回值。

新实现把“找到媒体并解析脚本文本”留给剧情/资源调用者，把 open、wait、decode、copy、
advance、service、close 和进度查询固定为 `LegacyVideoBackend` / `LegacyVideoPlayer`。
活动位仍由 app/runtime owner 持有，decoder 不拥有窗口或最终 present。

## 4. 当前兼容占位与最终后端

当前 `ImmediateCompleteLegacyVideoBackend` 对 begin 明确返回 `completed`，不创建句柄、
不设置视频活动位、不写 framebuffer。它只用于编解码后端尚未实现时让剧情播放请求继续，
属于“避免旧媒体依赖阻断新系统启动/推进”的隔离兼容例外，不声称已经播放视频，也不改写
已实现的真实播放器状态机。

音频和视频的压缩媒体处理最终只实现一次：项目自有的 `libffmpeg` 动态库负责 MP3、
Bink video、Bink audio、容器解复用、重采样和像素转换；主程序只加载 OpenSWD3 自己的
稳定 stream/video ABI，不直接包含或散布 FFmpeg API。当前阶段不链接 FFmpeg，也不自行
实现 Bink 解码器。

## 5. 验证

`legacy_video_test.cpp` 的 fake backend 固定：

- 打开、负音量静音、`0x8000` 上限、失败错误和 close 的一/零返回语义；
- wait 非零时只有 wait 调用，没有隐含进度、decode、copy 或 present；
- decode→copy→总帧数→当前帧号→advance→service 的精确顺序；
- 320×200 视频在 640×480 上得到 `(160,140)`，固定传入高 480 与 RGB565 surface；
- copy 零仍报告旧失败分支并继续 present；
- 终止帧先 present 再 close，以及 `0x00484DA0` 的正负进度；
- 立即完成占位不创建活动状态、不产生假帧。

真实 Bink 帧、音频与原版 framebuffer 差分仍是 `blocked_runtime_oracle`；需要时只准备
Frida spawn 工具并等待用户运行原版，OpenSWD3 不自行启动原 EXE。
