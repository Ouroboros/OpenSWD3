# 普通世界玩家控制与遇敌协调汇编证据：0x00402F80

状态：顶层控制流程已确认；`0x004038DB..0x00404094` 的方向、动作、移动边界与坐标前置合同已实现，完整入口仍在 B7

来源：`swd3.exe` 完整汇编

函数范围：`0x00402F80` 至 `0x004040A4`

独立输出：汇编回退；IDA 反编译器没有生成伪码

直接调用者：`0x0040A570`

调用约定：无栈参数

返回：全部调用点不读取；函数没有统一的显式返回值契约

## 1. 顶层职责

本函数在普通世界分支中紧跟 `0x00427300` 执行。两者职责不同：

- `0x00427300` 主要消费鼠标命中，处理 UI、NPC Talk 和地图格 Talk。
- `0x00402F80` 主要处理玩家方向控制、面向交互、碰撞事件、打开菜单和随机遇敌。

此外，`0x00402F80` 的前半段包含一组受隐藏门控保护的开发/调试热键。

## 2. 当前玩家记录

函数按当前玩家索引 `[0x004AB378]` 定位 216 字节角色记录：

```text
player = 0x004BABA8 + index × 0xD8
```

本函数直接使用的已确认偏移包括：

```text
+0x04  世界 X 坐标
+0x08  世界 Y 坐标
+0x10  角色状态位
+0x48  当前动作/移动状态
+0x4C  上一动作/移动状态
+0x74  八方向编号
+0x78  上一方向编号
+0x84  动作帧/过渡状态
```

这里只固定访问语义。`+0x10` 的全部状态位和 `+0x48` 的业务枚举仍不在 P2 提前命名。

## 3. 隐藏调试热键块

入口首先检查 `[0x004CAE98] == 1`，再对 `0x004B8748` 输入对象连续查询四个扫描码。全部满足时设置内部位编号 `0x52`。

只有 `sub_40DC50(0x52)` 非零时，后续调试热键才会执行。已确认效果包括：

- 切换高优先级调试/菜单状态。
- 切换若干全局调试开关。
- 调整一个限制在 `1..64` 的参数。
- 打开资源对话框。
- 增加 1000 银币。
- 遍历物品编号 `0x65..0x4AF`，对一组允许类别各加入十个物品。

多个分支直接调用 `Sleep(150..500 ms)` 做防连按，并在完成后提前返回。它们会改变帧时序，不能混入正常移动路径。

P2 只把这组逻辑标记为开发功能；扫描码与每个开关的最终用户命名不影响正常世界规则，留待兼容选项设计时决定是否暴露。

## 4. 普通世界控制门控

退出调试块后，函数清零一次性交互状态 `[0x004A99F4]`，并检查四个移动/过渡门控：

```text
[0x004A9488]
[0x004A948C]
[0x004B7518]
[0x004B7920]
```

四者都为零时，本帧才允许开始新的玩家控制。

此外，下列状态也会阻止正常控制主体：

- `[0x004CAE94] != 0`
- `[0x004B8740] != 0`

这保证特殊模式和其他角色过渡不会与世界移动并行执行。

## 5. 打开菜单

当输入记录 `[0x004B7D70]` 非零、其状态 `[0x004B7D7C] == 1`，且 Talk 上下文 `[0x004B72C4] == 0xFFFF` 时，函数执行：

```text
[0x004B8740] = 0x80000001
return
```

这就是普通世界进入 `0x00439FD0` 菜单模式 1 的直接键盘/控件路径。

## 6. 面向方向交互

另一路确认输入使用当前玩家方向 `[player + 0x74]`，通过两张方向偏移表和 `0x00404C00` 搜索玩家面前的角色。

若命中角色且 Talk 空闲：

1. 根据双方位置调用 `0x0040E030` 计算朝向。
2. 必要时通过 `0x004321E0` 更新 NPC 动作。
3. 令 NPC 与玩家相向。
4. 把命中角色的 Talk id、GUID、位置和状态复制到 `0x004B72A0` Talk 上下文。
5. 清除一次性交互状态。

诊断字符串为：

```text
RoleEventBy.GUID[%d].Talk[%d].Ridx[%d]
```

这条路径与 `0x00427300` 的鼠标 NPC Talk 使用同一 Talk 上下文，但命中算法不同：这里按玩家面向和角色碰撞范围搜索。

## 7. 四方向输入和八方向组合

四组输入状态分别生成：

```text
水平 -1
水平 +1
垂直 -1
垂直 +1
```

对角输入会把玩家 `[+0x74]` 映射为相应八方向编号。按键重复状态还会更新 UI/列表选择索引 `[0x004CAE7C]`，其上下界由 `0x0040DB40` 返回的链表节点数限制。

在特定位编号 `0x14` 未启用时，`0x004040B0` 会根据地图阻挡位调整对角分量，避免简单地把两轴移动直接叠加。

## 8. 角色和地图碰撞事件

函数用 `0x00404610` 查询移动后玩家足迹。调用契约在本入口表现为：

```text
sub_404610(player_index, dx, dy, &hit_role_index)
```

- 返回值为零：本次没有可触发的碰撞事件。
- 返回值非零：低 16 位作为事件/Talk 标识继续处理。
- 输出索引不是 `-1`：命中一个 216 字节角色记录。
- 输出索引是 `-1`：按返回标识查询地图事件链表。

地图事件路径建立特殊 Talk 上下文：

```text
[0x004B72C4] = 0xFFFD
```

并从事件记录 `+0x08` 读取 Talk id，结合当前玩家位置和方向表写入 Talk 坐标。

角色碰撞路径会让双方相向，复制被撞角色的 Talk id、GUID 和状态。诊断字符串为：

```text
RoleEventByCollision.GUID[%d].Talk[%d].Ridx[%d]
```

两条路径都要求当前 Talk 上下文仍是 `0xFFFF`，避免在已有剧情对话中再次触发。

## 9. 移动边界和动作更新

函数根据玩家世界坐标、相机偏移和地图像素范围计算八个边界门控，分别约束：

- 相机能否继续向四个方向滚动。
- 玩家能否继续向四个屏幕边缘移动。

移动分量随后写入四个过渡全局：

```text
[0x004B7518]
[0x004A9488]
[0x004B7920]
[0x004A948C]
```

函数比较新旧方向和动作状态，必要时清零 `[player + 0x84]`，并通过 `0x0040DD10` 把实际移动步长写入 `[0x004AB2D0]`。

无移动输入时，`[0x004CAD24]` 和 `[0x004C9A24]` 共同推进空闲计数；超过阈值后可把 `[player + 0x48]` 写成 `0x34`。存在移动输入时则重置空闲计数，并按碰撞、地图状态和速度门控选择动作值 `8` 或 `0x10`。

这些整数是原始动作状态，P2 不把它们提前改名为走、跑或待机动画枚举。

当前实现把该区间拆为两个可组合单元：

- `legacy_world_direction_input` 严格按左、右、上、下顺序消费输入记录 3、5、4、6，
  保留同时按键的覆盖结果、`held == 1 || (held & 7) == 7` 重复门和列表索引回绕。
- `legacy_world_player_motion` 恢复八个相机/玩家边界、四个移动过渡量、动作 `0/8/0x10/0x34`、
  步长翻倍/固定覆盖、空闲计数和 `0x004120F9..0x00412197` 的角色/相机坐标更新。

Linux Clang 全套 114/114、Windows LLVM `app` 118/118 CTest 通过。`0x004040B0`
对角阻挡修正、Talk 建立和随机遇敌仍属于本入口后续单元，因此不能把整个
`0x00402F80` 标为完成。

## 10. 随机遇敌选择

普通世界尾部只有同时满足以下条件才尝试遇敌：

- `sub_40DC50(ArgList + 0x1770) == 0`。
- 当前没有活动战斗 `[0x004CAEB4] == 0`。
- 内部位编号 `0x0C` 已启用。
- `[0x004A94AC] == 0`。
- Talk 上下文是 `0xFFFF`。

函数先递增遇敌步数/帧计数 `[0x004C9A20]`，再调用：

```text
sub_40DA60([0x004C9A20], 0)
```

`0x0040DA60` 的汇编顺序是：

1. 要求 `[0x004B896C] != 0`。
2. 立即调用 `sub_439070(100)` 取得随机值。
3. 用四组累计步数阈值选中当前概率段。
4. 将随机值与该段阈值比较；未通过则返回零。
5. 用玩家 tile 坐标查找 `[0x004A9A2C]` 链表中的遇敌区域矩形。
6. 从地图数据 `[0x004C9A10] + region_offset` 读取候选数量。
7. 调用 `sub_439070(candidate_count)`。
8. 返回对应的 16 位战斗编号，并清零 `[0x004C9A20]`。

第一次 `rand(100)` 发生在区域矩形查找之前。即使玩家不在任何遇敌矩形内，这次随机调用也已经消费；随机顺序属于兼容规格。

## 11. 从世界切入战斗

当 `0x0040DA60` 返回非零战斗编号时，函数按固定顺序执行：

```text
0x00485710
0x00485740
0x00433010
0x00431960
0x00451B10(battle_id)
```

随后：

- 写 `[0x004CAEB4] = 1`，激活战斗门控。
- 清零四个世界移动过渡全局。
- 解除当前地图文件映射，并关闭映射对象。
- 从角色索引 1 开始遍历 NPC，清除每个 `[record + 0x10]` 的位 `0x01000000`。
- 清零临时战斗请求 `[0x004A94AC]`。

地图映射在战后由 `0x0040A570` 的恢复分支重新建立。因此世界到战斗的资源生命周期跨越两个函数，不能把卸载和重映射都塞进战斗对象构造器而改变调用顺序。

## 12. 重写约束

- 本函数与 `0x00427300` 必须保持先鼠标交互、后玩家控制的帧内顺序。
- 216 字节角色记录步长和当前玩家索引计算必须统一建模。
- 面向交互、移动碰撞和鼠标 Talk 是三种独立命中入口，但最终写同一 Talk 上下文。
- 地图事件继续使用 `0xFFFD` Talk 上下文哨兵。
- 对角移动必须经过原阻挡位修正，不能只做两轴归一化。
- 随机遇敌必须保留两次随机调用的条件和顺序。
- 战斗建立前的音频/资源清理、地图解除映射和 NPC 状态位清理顺序必须保留。
- 调试热键要与正常控制逻辑隔离；是否在正式重写中默认启用属于产品决策，不得误删成未知死代码。
