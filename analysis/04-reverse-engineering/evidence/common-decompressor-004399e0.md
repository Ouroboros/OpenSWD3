# `0x004399E0` 公共解压器汇编规格

最后更新：2026-08-02

状态：函数内全部 token 分支已复核；与 LZO 2.10 逐分支对照完成，TSW 全样本逐字节一致

来源：`swd3.exe` 完整汇编

完整汇编是唯一真实依据。IDA 伪码只辅助定位。

## 物理接口

调用约定为 cdecl，函数实际读取的四个参数按汇编固定为：

```text
int decompress(
    const uint8_t* source,
    uint32_t source_size,
    uint8_t* destination,
    uint32_t* actual_output_size);
```

入口 `0x004399E0–0x004399F9` 将输入末端保存为 `source + source_size`，把输出长度先清零。原函数没有目标容量参数，也没有一般性输入/输出边界检查。

当前完整汇编列出四个直接调用者：`0x00426820`、`0x00433540`、`0x004338F0`、`0x00477F10`。全部有效调用环境已经在下一节闭环；TSW、ANI、存档/Fame 以及 `huge.lmf`/CM 的全部当前真实载荷均已完成分容器验证。

四个直接调用点都在这四个实参之前额外压入一个字面零，并由调用方按五个双字清栈；`0x004399E0` 从不读取第五项。`0x00426820` 只是参数顺序包装器：它把 `(source, destination, source_size, actual_output_size)` 改排成上述四个参数，同样额外压零，并把 EAX 原样返回。

## 全部有效调用环境与错误策略

机器目录已经覆盖：

- 4 个直接 `0x004399E0` 调用点。
- `0x00426820` 之外的 11 个包装器调用点。
- 合计 15 行物理/有效调用环境，分别属于 TSW、存档完整载入、存档槽预览、Fame 记录、Ani 帧、`huge.lmf` 地图块和 `Data/%d.cm` 生成。

最重要的调用层结论是：当前没有一个资产消费环境根据解压器 EAX 返回值分支。

- TSW 两条直接路径在调用后覆盖 EAX，只严格比较实际输出长度与描述符声明值。
- Fame 路径也覆盖 EAX，只严格比较实际输出长度与记录内声明值。
- 包装器确实原样返回 EAX，但它的 11 个调用点全部不检查；其中 10 个连实际输出长度也不检查，`0x0042660E` 只把实际长度指针继续交给 `0x00401B70`，不做相等比较。

所以函数自己的 `0/-8/-4` 约定和游戏调用方的接纳策略是两层不同规格。不能因为函数会返回 `-8`，就声称原游戏必然拒绝带尾字节的流；对 TSW/Fame 而言，只要实际输出长度相等，原调用方仍会继续。当前 TSW 和存档/Fame 样本都恰好消费输入；ANI 缓存路径则提供了调用者真实忽略 `-8` 并继续使用同字节输出的证据。

逐调用点的源指针、压缩长度、目标容量来源和错误策略见 `../inventory/decompress-call-sites.tsv`。

## token 状态机

下表只写物理公式，不用现代库名称替代原行为。`op` 是当前输出位置，`ip` 是当前输入位置。

| 分支 | token 范围 | 长度 | 回溯位置 |
|---|---:|---|---|
| 初始 literal | 首字节 `> 0x11` | `token - 0x11` | 无 |
| 普通 literal | `< 0x10` | 扩展后 `token + 3` | 无 |
| 短 match A | literal 后 token `< 0x10` | 3 | `op - 4*next - (token>>2) - 0x801` |
| 短 match B | match 状态 token `< 0x10` | 2 | `op - 4*next - (token>>2) - 1` |
| match `0x40..0xFF` | `>= 0x40` | `(token>>5) + 1` | `op - 8*next - 1 - ((token>>2)&7)` |
| match `0x20..0x3F` | `>= 0x20` | 扩展后 `(token&0x1F) + 2` | `op - (next_u16>>2) - 1` |
| match `0x10..0x1F` | `>= 0x10` | 扩展后 `(token&7) + 2` | 两段式 `0x4000` 回溯公式 |

长度为零的 literal、`0x20` match 和 `0x10` match 都按原循环处理连续零扩展字节：每个零增加 `0xFF`，首个非零字节再加各分支常量 `0x0F/0x1F/0x07`。

每次 match 完成后，`0x00439AC1–0x00439ADA` 读取刚消费偏移字节的低两位：

- 低两位为零：回到普通 literal token。
- 非零：原样复制 1 至 3 个 literal 字节，再直接进入下一个 match token。

这个状态跳转影响输入消费位置，不能改写成忽略低两位的普通 LZ 循环。

## 结束标记与返回值

`0x10..0x1F` 分支在减去最终 `0x4000` 前比较计算出的 match 指针是否等于当前输出指针。相等即结束标记，不执行复制。

`0x00439B29–0x00439B47` 先写实际输出长度，再比较输入指针与预先计算的输入末端：

| 条件 | 返回值 |
|---|---:|
| `ip == source_end` | `0` |
| `ip < source_end` | `-8` |
| `ip > source_end` | `-4` |

因此要取得函数级返回值零，输入必须恰好消费；只“解出预期字节”仍可能返回 `-8/-4`。这不等于调用方一定检查返回值。TSW 验证器对 20,091 帧同时记录了函数级恰好消费和调用方要求的输出长度。

## TSW 全样本实证

六个 TSW 样本的主流统计：

- 压缩输入：558,351,505 字节。
- 解压输出：1,378,998,573 字节。
- 20,091 帧全部返回等价成功条件。
- 每帧实际输出长度都等于描述符声明值。
- 每帧输入都恰好消费，没有尾字节容忍。
- 与本机 LZO 2.10 `lzo1x_decompress_safe` 的 20,091 帧输出逐字节完全一致，六包拼接哈希也逐项一致。

## 与标准 LZO1X 2.10 的逐分支对照

对照目标是本机 `liblzo2` 2.10 的 `lzo1x_decompress_safe`。LZO 包自带 `LZO.TXT` 将该接口明确归入 LZO1X；对照工具不使用网络，也不以库实现覆盖游戏汇编。

`../inventory/lzo1x-branch-compatibility.tsv` 把活动函数拆成 16 条可独立命中的状态/分支。结果为：

- 初始 literal 两种入口、普通/扩展 literal、两个上下文中的短 match、三档主 match 及其扩展、结束标记、低两位 `0..3` 的尾 literal 转移，公式均与 LZO1X 2.10 有效流一致；
- TSW 自然覆盖其中 12/16 条；共命中 72,098,622 次 `0x40..0xFF` match、44,694,699 次普通 `0x20..0x3F` match、9,829,819 次普通 `0x10..0x1F` match，以及 20,091 个结束标记；
- TSW 没有命中两种初始 literal 入口和两个短 match；四个手工合法流补齐这四项，原汇编安全转写与 LZO 2.10 均返回零且输出逐字节相同；
- 合并真实 TSW 与合法补充向量后，16/16 条状态均有执行证据。

### 纠正短 match B 的长度

本次逐分支对照发现旧文档和 `verify_tsw_decompression.py` 曾把 match 状态下 token `<0x10` 的复制长度写成三。汇编 `0x00439B13` 建立回溯指针后直接跳到 `0x00439AB6`，只执行两次字节写入，所以正确长度是二；三字节只属于 literal 后的 `0x00439A89` 分支。

修正后重跑 20,091 帧，声明长度和既有六包哈希全部不变。分支统计证明原因不是两种写法碰巧同值，而是当前 TSW 对该分支的命中数为零。`lzo1x-valid-branch-vectors.tsv` 中的 `short_match_after_match_len2` 向量专门执行该路径，汇编转写和 LZO 2.10 都输出三个 `A`：一个初始 literal 加两字节 match。

### 合法流等价不代表损坏输入等价

标准安全接口的五个控制向量固定了边界差异：

| 情形 | LZO 2.10 safe 返回 | `0x004399E0` 合同 |
|---|---:|---|
| 精确空结束标记 | `0` | 返回 `0` |
| 结束标记后多一字节 | `-8` | 返回 `-8` |
| 截断结束标记 | `-4` | 没有逐读边界检查，可能先越界；若仍到达尾比较才可能形成 `-4` |
| 目标容量少一字节 | `-5` | 没有容量参数，直接越界写 |
| match 指向输出起点之前 | `-6` | 没有 lookbehind 检查，直接越界读 |

因此已证明的是“LZO1X 2.10 对所有当前 TSW 有效流及四个补充合法分支向量字节等价”，不是损坏输入上的机器行为等价。安全接口新增的 `-5/-6` 在原四个直接调用者现有错误策略中也没有对应值。

同一 EXE 还包含无直接调用交叉引用的 `0x00439C20` LZO 形态快速例程。它采用双字超前复制并在逻辑指针上回退，且尾部另有不同检查；活动资产路径均调用 `0x004399E0`，所以不能拿这个未调用例程替换游戏真值或解释当前输出。

## 替换结论

`0x004399E0` 的有效格式可以确认是 LZO1X 兼容流，不再只是“高度疑似”。LZO 2.10 安全解压器可以作为合法游戏资源的实现候选，因为全量 TSW 和补充状态向量均已字节等价。但仍不能把“合法流可替换”偷换成“任意输入域无条件等价”，原因是：

- 原函数没有目标容量参数。
- 原函数对损坏输入可能先越界再到达返回比较。
- 现代安全解压接口会在原函数越界读写的位置提前返回 `-4/-5/-6`。
- 当前全部已知真实资产流都保持合法输入；尚未等价的是原函数在损坏输入上的无边界读写行为。

实现阶段若采用现代库，必须把安全接口及错误码映射隔离在资源平台层；有效资源结果服从本次字节回归，游戏层调用者仍保留各自忽略 EAX、只看输出长度或继续传递长度的原策略。

## ANI 对调用边界差异的实证

19 个 ANI 文件的 5312 帧已经按 `0x004158C0` 全量遍历。4623 个非空帧首次建立节点时只传 `record_size-12`，LZO 2.10 返回零；缓存重读传完整记录，结束标记后多出 12 字节链字段，统一返回 `-8`，但两条路径的 226,892,398 字节命令输出逐帧相同。调用者忽略 EAX 的结论因此有真实 `-8` 样本，不再只是静态可能性。

另有 689 个大小恰好 12 的零载荷帧，首次路径完全跳过解压。缓存路径若回访则会把元数据和暂存区陈旧尾部交给无边界函数，不能由安全库固定错误码代表。完整记录链、span 边界和 12 字节末帧/调色板重叠见 `ani-container-and-lzo-boundary.md`。

## 存档与嵌入 Fame 实证

40 份现有存档都由固定前缀、四个普通八字节压缩头、三个原样扩展区和一个非对齐 Fame 压缩头组成。每份恰有五条有效 LZO 流，共 200 条、941,822 字节输入和 1,666,172 字节输出。

200 条流全部由汇编转写精确消费并生成声明长度；LZO 2.10 安全接口也全部返回零，输出逐字节相同。四个普通块调用点仍原样忽略 EAX/实际长度，Fame 覆盖 EAX 但严格比较实际长度。物理布局、截断版本门和逐流哈希见 `save-container-and-lzo-boundary.md`。

## LMF 与 CM 实证

`huge.lmf` 的 309 张有效地图共定位出 309 条地表网格流、16 条索引对象流和 769 条 CM 分块流。1,094 条流的 410,310,015 字节输入全部精确消费，生成 838,618,552 字节完整输出；LZO 2.10 安全接口逐条返回零并与汇编转写字节一致。

CM 调用提供另一项调用层差异：每条流都解出完整 1,024,768 字节，但最后一块只把剩余前缀写入缓存；全包主动丢弃 158,144,256 字节已解压尾部。目标容量仍按原公式多分配 1,000 字节，调用者忽略 EAX 和实际输出长度。完整尾索引、三种头、逐流哈希和写入前缀见 `lmf-container-and-lzo-boundary.md`。

## 1:1 重写约束

- 有效流的 token 分支、长度扩展、match 距离、重叠复制和低两位 literal 必须逐项保持。
- 结束标记位置和 `0/-8/-4` 返回条件必须保留。
- 解压函数必须保留输入是否恰好消费所决定的返回值；调用层同时必须保留各自“忽略返回值/只看输出长度/继续传递输出长度”的真实策略，不能统一改写成遇到非零一律失败。
- 标准 LZO1X 安全接口已在全部当前已知真实资产流上得到逐字节等价证据；该结论仍不覆盖损坏输入域，也不允许统一改变各调用者忽略返回、只比长度或丢弃输出尾部的策略。
- 若未来为新系统安全性增加容量检查，必须放在不改变合法游戏数据结果的隔离边界，并保留原算法回归向量。
