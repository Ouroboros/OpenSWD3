# LMF 地图头 `+0x18` 索引对象目录 `0x0042642D..0x00426659`

状态：B2.19 已实现；`assembly_exact`、`asset_verified`、`platform_adapted`、`blocked_runtime_oracle`

完整汇编是唯一行为真值。IDA 伪码和符号名只用于定位。本单元恢复地图头 `+0x18` 指向的相对偏移目录、每个 0x1A 字节对象头、压缩负载读取及公共解压调用；`0x00401B70` 对输出内容的后处理留给对应消费模块。

## 1. 目录与对象头定位

`0x0042642D..0x0042644D` 按 32 位加法 seek 到 `map_offset + header.offset_18`，并在一基 seek 返回零时结束地图装载。随后固定请求读取 0x2000 字节，但不检查读取返回值。

目录物理布局为：

```text
u32 object_count
u32 relative_object_offset[object_count]
```

原代码按 `object_count * 4` 分配独立偏移数组并复制表项，分配失败时结束装载；计数随后按有符号值判断是否进入循环。每项在 `0x004264C5..0x004264DD` 被实际用于 seek `map_offset + relative_object_offset`，失败时结束装载。对象头再次固定请求读取 0x2000 字节，不检查读取结果。

## 2. 固定 0x1A 字节头

对象头的物理前缀为：

```text
+0x00  u16 field_00
+0x02  u16 field_02
+0x04  u16 field_04，当前装载代码不消费
+0x06  u16 field_06
+0x08  u16 field_08
+0x0A  u16 field_0a
+0x0C  u16 field_0c
+0x0E  u8  field_0e
+0x0F  u8  field_0f
+0x10  u8  field_10
+0x11  u8  field_11，当前装载代码不消费
+0x12  u32 destination_size
+0x16  u32 declared_compressed_size
+0x1A  byte compressed_payload[]
```

`0x00426519..0x0042657A` 把 `+0/+2/+6/+8/+A/+C` 六个 word 左移四位后写入运行时对象，并零扩展三个字节；`+4/+11` 不参与这段转换。B2 仍原样交付全部物理字段，但不在资源层执行坐标缩放或对象构造。

## 3. 实际读取长度与解压返回

`0x00426585..0x004265B0` 先按声明压缩长度和目标长度分别分配两个缓冲，任一分配失败都结束装载。`0x004265B6..0x004265F5` 再 seek 到 `map_offset + relative_object_offset + 0x1A`，并检查普通读取的 bool 返回。

普通读取会把长度参数改写为实际读取量。`0x00426600..0x0042660E` 传给公共解压包装器的是这个实际量，不是头内声明值。调用者不检查解压 EAX；随后把实际输出长度指针传给 `0x00401B70`。因此：

- 短读成功时，解压源长度必须是实际读取量；
- `input_not_consumed` 仍会继续进入后处理；
- 不能在游戏层新增“实际输出必须等于目标分配”的通用规则。

现代安全解压器在源耗尽、目标耗尽或非法回看时不会复现原程序的越界访问，本入口在这些状态停止并返回 `platform_adapted` 失败；合法成功和 `input_not_consumed` 都保留实际长度并交付对象结果。

## 4. 验证

合成 UT 覆盖两个对象、全部固定字段、未消费字节、正常流、尾随一字节的 `input_not_consumed`、零对象目录、目录越界、负向对象 seek，以及声明 12 字节但实际只读 6 字节的压缩负载。最后一项确认实际长度进入解压器并触发安全失败。

真实 `huge.lmf` 中 10 张地图共有 16 个索引对象，单图最多 4 个。16/16 个声明压缩长度等于实际读取长度，公共解压均成功且实际输出恰好填满目标；压缩输入共 6,887,901 字节，输出共 40,741,028 字节。按尾索引和目录顺序计算：

- 全部物理对象头字段 FNV-1a64：`0x2E8AFA07B54A528E`；
- 全部解压输出 FNV-1a64：`0xC2843348C085C2A2`；
- 既有逐字节 SHA-256：`51579e32f7b6ddb009231290f1f4dabc8e12720448714a01d2aa3757b2b062b8`。

Windows LLVM `core` 的 33/33 CTest 与显式真实档案测试均通过；原程序动态轨迹仍登记为 `blocked_runtime_oracle`。
