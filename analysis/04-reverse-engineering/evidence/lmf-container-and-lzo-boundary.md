# `huge.lmf` 容器、地图块与公共解压边界

状态：P3 外层和 B2.13 尾索引查找已闭环；全部当前压缩流及边界已验证；地图业务字段留给 P6。

## 证据口径

完整汇编是唯一逻辑真值。尾索引与地图载入依据 `0x00425CFA–0x004267D5`，CM 缓存/生成依据 `0x00426840–0x00427135`。所有偏移公式均回查实际寄存器和文件方法；IDA 伪码只用于定位。

样本固定为：

- `huge.lmf`：472,447,346 字节，SHA-256 `1fde9e3757a914a4235faa491733f06f236aa720ef8402522404636875833fc7`；
- `Data/mcache.dat`：384 字节，即 24 个 16 字节缓存目录项；
- `Data/0.cm` 至 `Data/23.cm`：当前两个非空缓存和 22 个空槽文件。

验证器只读这些文件，没有触发原程序会改写缓存的路径。

## 首双字与尾部索引

文件偏移零的 `u32` 是 `0x1C28E612`。`0x00425D12` 从当前文件位置读取这个双字，随后：

1. 用 `file_size - index_offset` 得到尾索引字节数；
2. 以 32 位有符号向零截断计算 `(tail_size - 1) / 16`，得到可查记录数；
3. 从 `index_offset` 开始读完整尾部；
4. 在每条 16 字节记录的 `+8` 以完整 `u32` 比较地图号；
5. 命中后从记录 `+0` 取得地图块文件偏移。

当前索引有 310 条记录：

```text
+0x00  u32 map_offset
+0x04  u32 physical_map_span
+0x08  u32 map_id
+0x0C  u32 reserved_zero
```

前 309 条为有效地图，地图号唯一，范围 2 至 500 但并不连续；末条是 16 字节全零哨兵。原函数读取全部 310 条，但减一计数公式使正常文件只查找前 309 条；若文件尾额外增加一个字节，哨兵会反常地进入查找范围。`+4` 的物理跨度虽不参与上述查找，却在全部 309 条中精确满足：

```text
map_offset + physical_map_span == next_map_offset
```

最后一张地图的等式右侧是尾索引起点。首地图从文件偏移 4 开始，因此 309 个地图块在 `[0x4, 0x1C28E612)` 无缝覆盖，没有洞、重叠或索引外数据。

## 当前地图块头

309 张地图的签名全部为 `MSF2`。汇编还保留 `MSFp` 分支，但当前包没有该变体，不能用当前样本把两条路径合并。

已用于 P3 边界的头字段：

| 相对偏移 | 宽度 | 当前用途 |
|---:|---:|---|
| `+0x00` | 4 | `MSF2` / `MSFp` 签名 |
| `+0x14` | 4 | 一个原样表区相对偏移，业务语义待 P6 |
| `+0x18` | 4 | 索引对象压缩块表相对偏移 |
| `+0x1C` | 4 | 另一原样表区相对偏移，业务语义待 P6 |
| `+0x20` | 4 | CM 分块压缩头相对偏移 |
| `+0x84..+0x8C` | 5×2 | 五个零扩展运行时量；本文暂称 width、height、field88、field8A、layers |
| `+0x96` | 变长 | NUL 结尾 CP950 地图名 |

四个 `+0x14/+0x18/+0x1C/+0x20` 偏移在全部样本中单调不减且均位于本地图物理跨度内。机器目录保留原值，不提前为 P6 的未知字段命名。

## 地表网格压缩流：`0x00426182`

原函数不是从固定 `+0xA0` 开始读取。`0x00425F6D–0x00425F94` 逐字节复制 `+0x96` 名称并把 EDI 留在终止 NUL 之后；`0x0042605B–0x0042606A` 用 `map_base + (EDI-header_buffer)` seek。因此当前原样表起点随名称长度变化，相对偏移范围是 `0x98..0xA5`。

原样表读取量为：

```text
raw_table_size = width * height * layers * 4 + 4
```

原样表最后一个 `u32` 在当前 `MSF2` 分支成为紧随其后的压缩长度 `C`。物理组织是：

```text
raw_table[raw_table_size - 4] = C
compressed_payload[C]
u32 post_surface_record_count
```

`0x00426160–0x00426182` 为目标分配 `width * height * 4` 字节，传 `C` 给公共解压器，然后忽略 EAX 和实际输出长度。当前 309 条流全部恰好填满这个目标；压缩输入 712,935 字节，输出 9,830,932 字节。

压缩负载后的双字由后续原样记录路径消费，当前值为 0 至 21。它不是压缩流尾部，不能把 `C+4` 一并交给解压器。

## 索引对象压缩流：`0x0042660E`

地图头 `+0x18` 指向：

```text
u32 object_count
u32 relative_object_header[object_count]
```

每个相对地址指向一个至少 0x1A 字节的对象头：

```text
+0x12  u32 destination_allocation_size
+0x16  u32 compressed_size
+0x1A  byte compressed_payload[compressed_size]
```

当前 309 张地图只有 16 条此类流，单图 0 至 4 条。原调用者忽略解压 EAX，但把实际输出长度指针继续传给 `0x00401B70`；不能把“下游收到长度”误写成“调用者要求等于分配量”。当前样本的 16 条恰好都填满分配：6,887,901 字节输入生成 40,741,028 字节输出。

## CM 分块流：`0x00426FDB`

地图头 `+0x20` 指向一个固定读取 `0x1A8` 字节的 CM 头。当前用于定位的字段：

```text
+0x10  u32 total_bytes_written_to_cm
+0x14  u32 chunk_output_size
+0x1C  array of 8-byte entries; each entry +0 is compressed_size
+0x1A8 sequential compressed payloads
```

当前 309 张地图的 `chunk_output_size` 恒为 1,024,768。`0x00426F41–0x00426F6F` 的目标分配并不是这个值，而是：

```text
destination_capacity = chunk_output_size + chunk_output_size / 1024
                     = 1,025,768
```

循环次数按原除法是：

```text
chunk_count = (chunk_output_size + total_bytes_written_to_cm)
              / chunk_output_size
```

当前 `total` 都不是整块倍数，所以结果等于普通向上取整；重写仍应保留原公式，不能靠当前样本改写。每轮从 8 字节表项取压缩长度，但压缩负载在 `+0x1A8` 后紧密连续。

### 末块丢弃不是解压短输出

全部 769 条 CM 流实际都解出完整的 1,024,768 字节。`0x00426FE3–0x00427015` 只把：

```text
min(remaining_total, chunk_output_size)
```

字节写入 `.cm`。所以每张地图的末块有一段已解压但被丢弃的尾部。全包统计：

- 402,709,179 字节 CM 压缩输入；
- 788,046,592 字节完整解压输出；
- 629,902,336 字节会写入 CM；
- 158,144,256 字节末块尾部被主动丢弃。

不能让安全库把末块目标长度设为 `remaining_total`，否则会在原程序成功解压完整块的位置返回目标越界，也无法复现被丢弃字节。

全部 CM 压缩负载结束后，每个地图块到其物理末端统一还剩 `0x60` 字节。该尾部不属于 LZO 输入，业务含义留给 P6。

## 当前 `Data/*.cm` 缓存

`mcache.dat` 的 24 个 16 字节项中，当前只有两个活动项：

- 槽 0：地图 24，声明 3,706,880 字节，`Data/0.cm` 文件大小相等；
- 槽 1：地图 81，声明 713,728 字节，`Data/1.cm` 文件大小相等；
- 槽 2..23：地图号为 `0xFFFFFFFF`，对应 `.cm` 文件大小为零。

现有两个 CM 文件的字节不等于原 LZO 输出的直接拼接。原因与汇编一致：`0x00426FF5–0x00427003` 在全局像素位数等于 16 时，先调用 `0x004238B0` 原地转换再写文件。P4 已证明两文件共 4,420,608 字节均由 `0x00423920` 的 RGB555→RGB565 公式逐字节精确生成，见 `pixel-format-selection-and-cm-cache.md`；这证明缓存生成时的 surface mask，而不改变本文的源分块边界。

## 全量 LZO 对照

`tools/build_lmf_container_inventory.py` 按上述三种环境枚举 1,094 条真实流，并分别执行汇编状态机安全转写和 LZO 2.10 `lzo1x_decompress_safe`：

| 环境 | 流数 | 压缩字节 | 完整输出字节 |
|---|---:|---:|---:|
| 地表网格 | 309 | 712,935 | 9,830,932 |
| 索引对象 | 16 | 6,887,901 | 40,741,028 |
| CM 分块 | 769 | 402,709,179 | 788,046,592 |
| 合计 | 1,094 | 410,310,015 | 838,618,552 |

结果：

- 1,094/1,094 条汇编等价流都精确消费输入，函数级返回零；
- 1,094/1,094 条 LZO 2.10 安全调用返回零；
- 每条完整输出与汇编转写逐字节一致；
- 按尾索引顺序、每图“地表→索引对象→CM 块”拼接的完整输出 SHA-256 为 `382a63d7b8179590f584ee34f6208c7a3d6ae062d24c34c66dbab5355e31f312`；
- 同序只拼接调用者实际保留前缀的 SHA-256 为 `6d7d1dc9faea2712dddb67fb0b18dd5f908cc5ad30f68e194ba8632eb8818c9a`；
- 当前 LMF 自然覆盖公共状态机 12/16 类分支，没有覆盖两个初始 literal 和两个短 match；此前合法补充向量已覆盖这些状态。

这完成了公共解压器全部已知真实资产环境的合法流对照。结论仍不扩展到损坏输入：原函数没有源/目标/lookbehind 安全检查，现代安全接口会提前返回不同错误。

## 1:1 重写约束

- 文件首双字和尾部 16 字节索引是查找真值；不能把地图号当连续数组下标。
- 当前只出现 `MSF2`，仍须保留汇编中的 `MSFp` 分支合同，直到版本资产证明可移除。
- 地表流起点跟随 NUL 名称末端，不是固定对齐位置。
- 地表压缩长度前置、记录数后置；后置双字不得交给解压器。
- 对象调用者只把实际长度传给后处理器，不在游戏层新增统一严格检查。
- CM 必须按原容量解出完整块，再只写有效前缀；158,144,256 字节当前丢弃尾部属于格式行为。
- CM 写入前只转换调用者实际保留的前缀；当前缓存已由 P4 证明使用 RGB555→RGB565，不能改成直接写入或转换完整解压块。
