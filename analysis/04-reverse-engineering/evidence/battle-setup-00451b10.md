# 战斗建立入口汇编证据：0x00451B10

状态：P2.2 顶层建立流程已确认；完整战斗字段留待 P7

来源：`swd3.exe` 完整汇编

函数范围：`0x00451B10` 至 `0x004527DB`

直接调用者：

- `0x00402F80`
- `0x0040A570`
- `0x00469D20`

调用约定：一个 32 位栈参数，调用者清栈

参数有效部分：低 16 位战斗编号

返回：调用者不读取；函数没有可靠的统一返回值契约

## 1. 参数和入口状态

函数首先把参数低 16 位写入 `[0x0053C052]`。

随后停止/整理一条 Miles 流路径，并清空或重置大量战斗全局区域。已确认的初始化形式包括：

- 多个连续数组用零填充。
- 多个 18 项数组用 `0xFFFFFFFF` 填充。
- 参战者、临时效果、选择、坐标和计数全局归零。
- 四个状态 `[0x004FF578]` 至 `[0x004FF584]` 写一。
- `0x004C9708` 起的对象先由 `0x0040DC00` 重置，再写入固定字段。

这些操作证明 `0x00451B10` 是一次完整战斗实例建立，而不是只读取战斗编号。

## 2. 初始队伍选择

函数依次查询内部位编号：

```text
0x1E, 0x1F, 0x20, 0x21
```

每个非零位会：

- 把 `0x00521398` 起的对应字节写一。
- 增加 `[0x0053BCE4]`。

随后按原始四个位置的活动状态，建立 `[0x004A75C8]` 起的紧凑索引表。

因此 `[0x0053BCE4]` 在此阶段可确认是玩家侧初始参战人数，而 `[0x004A75C8]` 是从紧凑参战槽到原队伍槽的映射。

## 3. 战斗窗口与输入呈现状态

进入文件读取前，函数执行：

- `GetWindowRect(hWnd, &Rect)`。
- 把字号/绘制状态 `16` 写入字体 renderer `0x004C9A28 + 0xFE0`。
- 计算两组 16 位颜色值。
- 绑定/更新战斗图形对象。
- 把两组战斗鼠标相关坐标写为 `(320, 200)`，再调用 `0x00437430` 把 DirectInput 绝对轴基准重定位到该逻辑坐标。
- 依次调用 `0x00451AE0` 和 `0x00451A90`，释放后重新建立三项战斗显示对象。

这里固定的是原调用顺序。`0x00435650` 只写字体 renderer 字段，不是输入对象重建；战斗建立对输入的直接动作是 `0x00437430` 的鼠标坐标重基准。新平台不需要复制 DirectDraw 对象，但输入中心点和显示资源重建边界必须保留。

## 4. figtalk.dat 战斗脚本

函数以战斗编号低 16 位调用 `0x0046E0B0`。

该下游函数在 `[0x004A7B5C] != 0` 时使用 `figtalk.dat`：

1. 通过全局句柄惰性打开文件。
2. 从等价于 `0x200 + battle_id × 4` 的位置读取一个 32 位偏移。
3. 转到 `0x200 + offset`。
4. 分配并清零 0x8000 字节。
5. 固定读取 0x8000 字节。
6. 把缓冲区地址同时写入 `[0x0053CE84]` 和 `[0x0053CE88]`。

`[0x0053CE84]` 已在 P1.6 确认是 `0x00469D20` 读取的当前战斗指令指针。因此 `0x00451B10` 在建立战斗时同时装入战斗脚本。

原函数只用 `test eax, eax` 检查 `CreateFileA` 结果；`INVALID_HANDLE_VALUE == -1` 会被误判为成功。这是旧程序的实际错误边界，初步还原将它作为兼容规格记录，不主动修复。若 64 位 API 或新系统导致正常资源无法打开，只允许在平台文件适配层做最小例外，不得改动战斗建立逻辑。

## 5. battle.ffd 索引和固定记录

函数构造：

```text
<基础路径> + "battle.ffd"
```

并通过 `0x0045F130`、`0x0045F1B0` 读取。

下游汇编确认：

- 文件头读取长度固定为 `0x2714` 字节。
- 战斗编号在 `0x1F48` 起的一组计数/索引数据中定位。
- 固定记录大小为 `0x10C` 字节。
- 记录区起始偏移为 `0x2714`。
- `0x00451B10` 传入的变体序号为零，即选择该战斗编号的第一个记录。
- 记录写入全局缓冲 `0x004FF1E0`。

记录中的：

- `word [0x004FF278]` 被写入 `[0x0053BCE0]`，并作为敌方数量循环上界。
- `word [0x004FF204]` 被写入 `[0x0053BDDC]`，同时参与战斗背景资源建立。

若 `[0x0053BCE0] == 0`，函数写诊断后提前返回，不建立后续敌我对象。

`0x0045F130` 和 `0x0045F1B0` 的返回值在本调用点没有被检查；原程序依赖后续记录内容继续门控。

## 6. 战斗背景资源

函数以 `sub_439070(4) + 1` 生成一个 16 位值，并结合 `battle.ffd` 记录字段调用 `0x00451940`。

`0x00451940` 明确打开 `all_map2.tsw`，解出资源后建立战斗背景相关对象；在满足记录字段条件时还调用额外的图像处理路径。

因此战斗建立阶段已经包含背景资源选择，不是等到 `0x00453200` 第一帧才加载全部画面。

## 7. 敌方对象

敌方数量 `[0x0053BCE0]` 大于零时，函数逐项建立对象。

敌方对象基址和步长由实际地址运算确认：

```text
base   = 0x00525508
stride = 0x2B28
slots  = 8
```

每个敌方记录至少执行：

- 对象重置/构造。
- 从 `battle.ffd` 记录数组读取三个 16 位字段。
- 写入一个 32 字节显示槽的资源编号和坐标。
- 当 `[0x0053C000] == 1` 时，以 640 为基准镜像 X 坐标并设置对象镜像状态。
- 建立角色图像/动作资源。
- 按记录位决定附加状态。

八个槽位上限由 `0x00451A20` 对同一对象区间的循环再次印证。

## 8. 玩家侧对象与阵型

玩家侧初始参战人数来自 `[0x0053BCE4]`，由四个活动位形成的机器范围是零至四。

函数为一、二、三、四人分别写死不同的屏幕坐标阵型。显示槽：

```text
base   = 0x0053AF70
stride = 0x20
```

当 `[0x0053C000] == 1` 时，阵型 X 坐标同样围绕 640 镜像。

玩家侧完整战斗对象区：

```text
base   = 0x005029D0
stride = 0x2F34
slots  = 10
```

每个初始队伍成员通过 `[0x004A75C8]` 映射回原队伍槽，然后绑定：

- `0x004C8AD0` 起、步长 64 字节的角色状态。
- `0x004A9490` 起的每角色值。
- `0x004A9940` 资源集合。
- `String` 起、步长 16 字节的名字。
- `0x0053AF70` 起的显示槽。

随后函数从对象查询多个数值对，执行整数/浮点比值换算，并把结果写入战斗数组。P2 只固定数据流，不为这些比值提前猜测攻击、防御或生命等业务名称。

## 9. 最多两个额外玩家侧成员

函数检查八个内部位：

```text
0x22, 0x23, 0x26, 0x2C, 0x2D, 0x2E, 0x2F, 0x31
```

对应资源/角色编号表为：

```text
3, 4, 10, 33, 34, 37, 38, 40
```

规则已经确认：

- 活动位不超过两个时，按表顺序加入，最多两个。
- 活动位超过两个时，用 `sub_439070(8)` 反复随机选择尚未使用且活动的项，直到加入两个。
- 额外成员计数写入 `[0x0053BF0C]`。
- 每加入一个成员，同时增加玩家侧总参战人数 `[0x0053BCE4]`。
- 额外成员使用固定坐标，并同样受 `[0x0053C000]` 镜像。

这一步的随机调用顺序属于战斗确定性的一部分，重写时不能把“随机选两个”替换成无序容器抽样。

## 10. 收尾初始化

玩家和敌方对象建立后，函数依次调用：

```text
0x0045B0E0
0x0045B190
0x0045B5A0
```

随后：

- 为每个敌方对象执行 `sub_439070(6)` 次的附加初始化循环。
- 为每个玩家侧对象调用 `0x00478380`。
- 根据玩家侧总数、额外成员数和两个战斗计数计算一个边界条件；满足时写 `[0x0053BCEC] = 0x67`。

三个收尾函数和 `0x67` 的业务枚举仍留给 P7，但它们发生在战斗建立返回前。

## 11. 已确认语义名

P2 语义名：按战斗编号重置战斗状态、加载 figtalk/battle.ffd、建立背景、敌方与玩家侧对象、选择额外成员并完成战斗收尾初始化。

关键重写约束：

- 参数在两个数据文件中都按低 16 位战斗编号使用。
- `figtalk.dat` 脚本缓冲必须在战斗更新入口执行前准备。
- `battle.ffd` 使用 0x2714 字节头和 0x10C 字节固定记录。
- 初始队伍只看四个位，随后最多加入两个额外成员。
- 阵型和镜像坐标是固定整数，不应先改造成自适应布局。
- 函数以副作用完成初始化，不能依赖 IDA 推测的返回类型。
