# 剧情 VM opcode 0–24 汇编语义批次

## 证据口径

本批次逐条人工回查 `sub_427920` 完整汇编，固定 opcode `0..24` 的混合字节布局、状态读写、helper 调用、IP 推进、同帧继续、跨帧让出和异常边界。汇编是唯一真实依据；工作名称只用于区分操作，不宣称已经恢复原开发者命名。

`inventory/story-vm-opcode-semantics-000-024.tsv` 是本批次的逐值规格。生成器同时读取已锁定的一级分派和长度目录，防止人工语义行与入口/物理长度脱节。

## 直接状态访问底稿

在人工语义表之前，`tools/build_story_vm_opcode_direct_effects.py` 对 198 个 opcode 的保守 CFG 提取了直接数据符号访问：

- 198 行 opcode 汇总；
- 1449 个逐指令证据点；
- 275 个直接符号，其中 157 个出现实际读/写，其他仅取地址；
- 581 个读点、416 个写点、19 个读写点和 433 个地址引用点；
- 114 个 opcode 的 CFG 内含直接写或读写，157 个含调用点。

这只是审计底稿，不是最终语义。普通条件分支仍采用过近似，例如 opcode 1–6 共用入口，底稿可能同时收录奇数/偶数变体的两侧；callee 内部的间接副作用又被刻意排除。逐 opcode 结论必须像本批次一样回到具体比较和数据流，不能把底稿列直接翻译成 C++。

## 操作与时序摘要

| opcode | 当前中性操作名 | 关键行为 |
|---:|---|---|
| `0` | 默认无效值 | 蜂鸣、诊断、不推进、跨帧让出；后续帧重复同一错误 |
| `1..6` | 六种文本/action 记录变体 | 从 `+2` 的混合载荷建立 `0x4C` 记录，扫描到 `%Q`，推进后让出 |
| `7` | 清文本控制 bit 31 | `dword_4A1360 &= 0x7FFFFFFF`，推进并同帧继续 |
| `8` | 设置下一文本附加值 | `dword_4CF738=1`，`dword_4A1364=u16(+2)` |
| `9` | 清文本控制 bit 30 | `dword_4A1360 &= 0xBFFFFFFF` |
| `10` | 修改角色 `+0x08` | 原诊断名 `ChangQQ`；角色存在/缺失走不同 helper 路径 |
| `11` | 修改角色 `+0x34` | 原诊断名 `ChangDir`；并将角色 `+0x10` OR `0x1000` |
| `12` | 设置角色位置 | 两个 16 位分量左移四位后传 `sub_42DAF0` |
| `13` | 请求角色 step 更新 | 条件调用 `sub_42E280`，消费后让出 |
| `14` | 等待角色 action 状态为零 | 忙时原 IP 跨帧重试；就绪时消费后仍让出 |
| `15` | 同文件重载剧情窗口 | `u32(+2)` 为 TALK payload 相对目标；IP 清零并同帧继续 |
| `16/17` | 按对象/角色 flag 反向条件跳转 | 扫描固定 72 个对象槽，分别在 `0x40000000` 清/置时跳转 |
| `18` | 轮询角色释放 helper | helper 返回零时不推进但同帧立即重试 |
| `19` | 清理所有 bit31 角色 | 从角色下标一开始遍历，不处理下标零 |
| `20` | 批量调度角色并等待就绪 | 自修改 bit14 的两阶段 6 字节记录命令 |
| `21/22` | 全局 bit 置/清条件跳转 | 通过 `sub_40DC50`，两者谓词严格互反 |
| `23/24` | 全部/任一全局 bit 条件跳转 | `u16` 列表以 `0xFF00` 结束，随后为 `u32` 目标 |

候选控制流图在当前资产中观察到了本批次 23/25 个值；opcode 0 和 13 没有样本。其余值共有从 2 到 5547 个不等的唯一物理指令位置。样本缺失不改变汇编结论，也不能据此删除 opcode 13。

## opcode 1–6：混合文本载荷不是普通字符串

六个值共用 `0x00427B8F`。`+2` 开始的字节既被读取为首个 16 位上下文/角色选择值，也整体传给 `sub_40AFF0`，随后以字节步进扫描到 `0x25 0x51`（`%Q`）。所以它不能简单建模成“opcode + C 字符串”：

- `0xFFF0` 会被替换为 `state+0x24`，而且写回当前脚本缓冲区；
- `0xFFFD` 走特殊上下文；
- 终止扫描无边界检查，并允许奇数字节长度；
- handler 分配并清零 `0x4C` 字节记录，调用 `sub_40AFF0` 填充，再由 `sub_40BB20` 接入 action/dialog 队列；
- 消费 `%Q` 后清回一组文本控制全局默认值，`ESI=0`，因此本帧让出。

变体差异由有效 opcode 本身决定：1/2 使用 mode 0，3..6 使用 mode 1，5/6 初始 record flag 为 `0x40`；奇数 1/3/5 还设置 record `0x10` flag、把选中角色 action 状态写一并递增 `dword_4A9920`。不能因为一级入口相同而合并成一个 opcode。

## 三种不同的等待模型

本批次已经出现三种不可互换的等待：

1. opcode 14：状态非零时不推进、`ESI=0`，返回主循环，下一帧重试。
2. opcode 18：`sub_42D920` 返回零时不推进，但无条件设置 `ESI=1`，在当前 `sub_427920` 调用内立刻重取同一 opcode；helper 若一直返回零会形成忙循环。
3. opcode 20：首次调度后设置脚本操作数字 bit14 并让出；后续帧检查所有记录。未全就绪仍让出，全部就绪才清高位、推进并同帧继续。

重写不能把这三者统一成 `sleep`、future 或“每帧推进一次”的抽象，否则会改变同帧执行数量和原始卡死边界。

## opcode 20 的自修改两阶段合同

操作数字布局：

```text
+0  u16 opcode
+2  u16 count_and_flags: low14=count, bit14=phase, bit15=forwarded flag
+4  count × { u16 role, u16 component_A, u16 component_B }
```

bit14 为零时，handler 按六字节步长解析记录。角色存在时调用 `sub_42DAF0`；分量 `0xFFFF` 会改用角色当前值。处理完成后执行 `byte [command+3] |= 0x40`，但不推进 IP。

bit14 已置时，handler 检查角色 `+0x10` 的 `0x02000000` 或 `sub_42E280(role)==2`。只有全部记录就绪才执行 `word [command+2] &= 0x3FFF` 并推进 `4 + 6×count`。opcode 169 虽共享 handler，却使用 12 字节记录，不能套用本行宽度。

## 条件 bit 列表的空表差异

opcode 23 对每个 `u16` bit id 直接查 `byte_4AB384`。终止值前所有 bit 都为一时跳转；由于空表从零开始满足“全部成立”，首项就是 `0xFF00` 时也会跳转。

opcode 24 统计至少一个置位项；空表计数为零，因此不跳转。两者都无终止符边界检查，顺序长度为 `8 + 2×count`。
