# `0x00439DE0..0x00439FC8` 特殊模式 Act 状态初始化

状态：接口级闭环；`assembly_exact`、`module_reassigned`、`deferred_to_special_modes`

来源：`swd3.exe` 完整汇编、两个调用者、三个被调函数和全局状态交叉引用。IDA 伪码只辅助定位，不作为行为依据。

## 1. 边界与生命周期

函数入口为 `0x00439DE0`，`0x00439FC8 retn` 结束；`0x00439FD0` 已是特殊模式顶层函数的独立入口。函数无参数，有两个直接调用者：

- `0x00424ECA`：总初始化读取主要数据后调用，随后重置 Talk/剧情状态。
- `0x0040F1BF`：重新读取游戏数据后调用，随后同样重置 Talk/剧情状态。

两个调用者都忽略 EAX。函数在最后一组赋值前把 EAX 写成 `0x232B`，随后不再修改，所以物理返回值碰巧为 `0x232B`；这不是调用者使用的成功码。

## 2. 18 个 Act 记录的重置

`0x00439DF0..0x00439EA2` 按固定顺序把 18 个全局记录地址传给 `0x0040DC00`：

```text
4FB970  FC790  FC840  FB810  FC450  FC518
FC328  FC6E8  FBA18  FB8D8  FC650  FBFA0
FC038  FC0D0  FC168  FBEE0  FC208  FC5B0
```

`0x0040DC00` 是 `asset_runtime` 已确认的 Act 记录重置 helper。它只写以下字段，不清零整个记录：

```text
+0x1C = -1    +0x20 = -1    +0x3C = -1
+0x42 = 0     +0x44 = 0     +0x46 = 0     +0x48 = 0
+0x90 = 0
```

因此重复初始化会保留其他字段。特别是 `FC650` 和 `FBEE0` 在本函数中只执行上述局部重置，不重新写 `+0x00/+0x08`；不能把整个记录统一 value-initialize。

随后写入的 Act 资源号和选择字段为：

```text
base    +0x00    selector field/value
FB970   0x232A   +0x08 = 0
FC840   0x232A   +0x08 = 1
FC790   0x232A   +0x34 = flag(0x49) ? 3 : 2
FB810   0x232A   +0x08 = 4
FC450   0x232A   +0x08 = 5
FC518   0x232A   +0x08 = 6
FC328   0x232A   +0x08 = 0x18
FC6E8   0x232A   +0x08 = 0x19
FBA18   0x232A   +0x08 = 0x1A
FB8D8   0x232A   +0x08 = 0x1B
FC208   0x232A   +0x08 = 3
FBFA0   0x232B   +0x08 = 0x2C
FC038   0x232B   +0x08 = 0x2D
FC0D0   0x232B   +0x08 = 0x2E
FC168   0x232B   +0x08 = 0x2F
FC5B0   0x233B   +0x08 = 0
```

函数入口还把特殊模式标志 `0x004FBED8` 清零。

## 3. 回调表与剧情标志

入口调用的 `0x00444FC0` 写入三组各七项的函数指针表：`0x004FBF80`、`0x004FC8DC` 和 `0x004FB8B0`。三组默认表都在索引 4、5 放置一对角色相关回调；当 `0x0040DC50(0x49)` 返回真时交换这两个索引。

`0x00439DE0` 随后再次查询同一个标志，独立决定 `FC790 + 0x34` 写 2 还是 3。不能缓存成一次调用后假定无副作用，也不能把回调交换和 Act 字段选择合成一个高层布尔状态。

`0x00444FC0` 的另一个调用者是特殊模式函数 `0x0043B480`。这些表和 Act 记录随后由 `0x00439FD0`、`0x0043A610`、`0x0043A880` 及同族状态机读写、绘制；`0x0040EBF0` 的原诊断文本也确认记录用于 `Misc::DrawActData`。

## 4. 模块归属修正

旧目录只因地址紧邻 LZO 函数而把 `0x00439DE0` 机械归到 `resource_io`。完整汇编证明其真实职责是特殊模式的 Act 状态和回调初始化：

- 状态由 `special_modes` 顶层及同族 handler 消费和修改。
- `asset_runtime` 只提供共享 Act 记录重置/绘制能力。
- `story_scene` 只提供标志 `0x49` 查询。
- 两个外部调用者只是启动和数据重载时触发生命周期初始化，不取得状态所有权。
- 函数不读取文件、不解压数据，也不拥有资源容器。

因此 `module-function-ownership.tsv` 将该函数改归 `special_modes`。B2 只保留这份边界证据，不实现它；正式 C++ 状态应在特殊模式模块开始时建立。

## 5. 后续实现与验证门

特殊模式模块实现该单元前至少固定：

- 标志 `0x49` 为假/真时三组回调索引 4、5 和 `FC790 + 0x34` 的精确快照。
- 18 个记录的调用顺序、共享 reset 字段和 16 组显式资源/选择值。
- 连续调用两次时 `FC650`、`FBEE0` 未被 reset helper 覆盖字段的保留行为。
- `0x004FBED8` 清零和被调用者返回值不参与错误分支。
- 两个生命周期调用点的相对顺序，以及调用者忽略偶然 EAX=`0x232B`。

在这些状态的实际使用者和回调 ABI 尚未进入 `special_modes` 实施阶段前，提前创建 18 个无消费者的 C++ 全局对象不能证明兼容性，反而会固化错误所有权。
