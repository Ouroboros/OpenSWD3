| `0x960C` | `0x20` | 固定 32 字节存档文字槽 | `0x00407B0F–0x00407B43`；预览载入在 `0x00409727` 从此处复制字符串 |
| `0x962C` | `8+C0` | 压缩块 0：`u32 C0, u32 U0, C0 bytes` | `0x00407B4D–0x00407B8C`；`U0=0x400` |
| 前块末端 | `8+C1` | 压缩块 1：相同的八字节头 | `0x00407B97–0x00407BE1` |
| 前块末端 | `0x1C` | 七个原样 `u32` | `0x00407BEC` 起连续七次四字节写入；`0x004084B3–0x00408501` 读取 |
| 前段末端 | `8+C2` | 压缩块 2：相同的八字节头 | `0x00407CA1–0x00407EBE` |
| 前块末端 | `0x84` | 原样扩展 A：`0x40 + 4 + 0x40` | `0x00407ED2–0x00407F9F`；`0x00408997–0x00408A4B` |
| 前段末端 | `0x180` | 原样扩展 B | `0x00407FA4–0x00407FBA`；`0x00408A52–0x00408A6C` |
| 前段末端 | `4+F` | `u32 F` 加一个嵌入 Fame 记录 | `0x00407FBF–0x00407FED`；`0x00408A70–0x00408A8D` |
| Fame 后 | `0x84` | 原样扩展 C：两个 `u16` 加固定 `0x80` 字节 | `0x00407FFC–0x00408042`；`0x00408AB4–0x00408AE7` |
| 前段末端 | `8+C3` | 尾压缩块：`u32 C3, u32 U3, C3 bytes` | `0x00408047–0x004080C5`；`0x00408AED–0x00408B0E` |

40 个样本全部满足上述递推，尾压缩负载结束位置逐字节等于 EOF，没有未解释尾部。文件总计 2,508,462 字节，单文件大小为 61,723 至 63,464 字节。

机器可读的逐文件绝对偏移见 `../inventory/save-files.tsv`。这里的块名只是调研标签，不是尚未证明的游戏类型名。

## 五个压缩流

除 Fame 外，四个普通块头都按小端顺序保存：

```text
+0x00  u32 compressed_size
+0x04  u32 original_or_declared_output_size
+0x08  byte compressed_payload[compressed_size]
```

五条实际消费路径如下：

| 序号 | 调研名 | 解压调用 | 原目标容量 | 原调用者接纳策略 |
|---:|---|---|---|---|
| 0 | preview state | `0x00408371`、`0x0040976A` | 完整载入写固定全局；预览分配 `2*U0` | 两条路径均忽略 EAX 和实际输出长度 |
| 1 | primary state | `0x00408439` | `U1` | 忽略 EAX 和实际输出长度 |
| 2 | u16 state | `0x00408546`、`0x0040980B` | `2*U2` | 完整载入和预览均忽略 EAX 和实际输出长度 |
| 3 | embedded Fame | `0x00477F79`，由 `0x00408A7F` 进入 | 声明输出长度 | 不检查解压 EAX，但 `0x00477F85` 严格比较实际长度；外层又忽略 Fame 载入返回值 |
| 4 | tail pair | `0x00408B0E` | 固定 `0xA8` | 忽略 EAX 和实际输出长度；随后只消费两个 `0x34` 字节区 |

这里必须保留三处容易被现代化实现抹平的差异：

- 块 0 在两个调用环境中的目标内存策略不同，不能凭样本输出固定为同一种分配方式。
- 块 2 的分配是声明长度的两倍，即使当前 40 份样本的实际输出都恰好等于声明长度。
- 尾块头的 `U3` 在全部样本中是 `0x68`，但完整载入固定分配 `0xA8`；不能把这两个量合并。

## 嵌入 Fame 记录

磁盘上的独立 `Fame.dat` 是 1024 字节的 512 个 `u16` 表，与这里的嵌入记录不是同一格式。

`0x00477C90` 生成的嵌入记录采用非对齐头：

```text
+0x00  u8  marker       // 当前写入值 1
+0x01  u8  zero         // 分配后清零留下
+0x02  u32 output_size  // 非对齐读取
+0x06  u32 compressed_size
+0x0A  byte compressed_payload[compressed_size]
```

外层 `F` 在全部 40 份样本中严格等于 `10 + compressed_size`。标记均为 `01 00`。`0x00477F10` 从 `+2/+6/+10` 取三个量，把压缩数据复制到临时缓冲后调用公共解压器；它覆盖解压 EAX，只比较写回的实际长度与 `+2` 声明值。

解压结果由三个连续分组组成。每组的物理跨度为 `10 + 14*count`，头部 `+4` 是 `u16 count`，之后是 `count` 个 14 字节记录。写入器只有在组非空时才把该跨度写到组头 `u32 +0`；空组的该字段保持零，但物理上仍占 10 字节。当前样本：

- 第一组 1 至 33 条；
- 第二组恒为 500 条；
- 第三组 0 至 26 条；
- 每份总计 501 至 554 条，三个物理跨度都精确闭合到声明输出末端。

`read_legacy_save_fame_groups` 现受检读取三个组头和每条 14 字节记录，保留组头剩余四字节，不将组跨度值冒充实际扫描边界；40/40 份真实原版存档的第二组 500 条且三组完整消费至块末端。`Save/0.sav` 按独立 inventory 为 `2/500/0`、跨度 `38/7010/0`，总消费 7058 字节。截断第三组头的合成输入被拒绝。该函数只解析物理记录，不发布战斗状态。LST `0x00477FBE–0x004780ED` 的三组链根分别为 `0x004ACBA8`、`0x004B9F00`、`0x004B8A00`，对应现有 `LegacyBattleFixedObjectState` 的不同索引；`0x00478110–0x00478212` 先清掉旧三组链。进一步核对 `0x00477FBE–0x004780ED`：按 `0x004ACBA8`、`0x004B9F00`、`0x004B8A00` 三根的顺序，每组把计数写入根 `+4` 的低16位；每条经 `sub_487C10(0x14)` 分配、清零五个 dword，前节点 `+0` 指向新节点，再将原记录完整14字节复制至新节点 `+4..+0x11`，余下2字节保持零。`0x00478110–0x00478212` 在读取前从三根释放旧链并各清零五个 dword；现有 `LegacyBattleFixedObjectState::fixed_count_nodes` 也被 `legacy_battle_fixed_count_chain` 按 token 查找使用，不能另起地址空间。受控物化复用现有 `LegacyBattleFixedObjectState::fixed_count_nodes` 与进程级 guest 地址预留；真实 `Save/0.sav` 在三根写入 2/500/0 条节点。SDL读档入口将该函数应用于持久的战斗固定对象状态；后续完整战斗生命周期仍待验收。

旧链释放已改为[共用实际释放函数](battle-fixed-chain-release-00478110.md)，
按根顺序从每条链尾部释放，释放后清前驱链接，再清该根。
删除先整体收集身份再批量释放的过程，保留后续根失败前已经完成的释放。
该修改只验收旧链释放，不替代整个Fame载入流程和实际续玩的验证。

## 截断兼容和错误行为

完整载入不是先验证完整格式再解析。它在若干扩展段之前比较当前绝对偏移与文件大小：

- `0x00408507–0x00408519` 在块 2 之前；
- `0x00408984–0x00408991` 在扩展 A 之前；
- `0x00408A44–0x00408A50` 在扩展 B 之前；
- `0x00408A6A–0x00408A6E` 在 Fame 之前；
- `0x00408AAA–0x00408AAC` 在扩展 C 之前；
- `0x00408AE3–0x00408AE7` 在尾块之前。

达到或越过文件末端时，函数跳过余下版本扩展并进入共同清理/默认状态路径。这是原载入器的版本/截断接纳行为，初步重写不得强行改成“必须具备当前完整尾部”后才允许读取。

相反，已经进入某一段后，大多数长度、分配和解压失败没有统一拒绝逻辑。公共包装器返回值与写回长度在四个普通块调用点全部被忽略；Fame 只检查输出长度。按 bug-for-bug 要求，这些事实先作为规格记录，不在调研阶段修复。

## 全样本解压结果

`tools/build_save_container_inventory.py` 对 40 份存档中的 200 条流同时执行：

1. 按 `0x004399E0` 汇编状态机的安全研究转写解压；
2. 用本机 LZO 2.10 `lzo1x_decompress_safe` 对同一有效流解压；
3. 比较返回、实际长度和全部输出字节；
4. 验证每个容器递推位置、Fame 外层长度、三组跨度和最终 EOF。

结果：

- 941,822 字节压缩输入生成 1,666,172 字节输出；
- 200/200 条汇编等价流都精确消费输入并生成声明长度，函数级返回为零；
- LZO 2.10 对 200/200 条均返回零，输出与汇编转写逐字节一致；
- 按逐文件、块序顺序拼接的总输出 SHA-256 为 `c7c88439df420d9125a939f7240918736ec84877eb6991c216fbb8a0357b415e`；
- 当前存档自然命中公共状态机的 11/16 类分支；没有新增 TSW/ANI 尚未覆盖的合法分支，但增加了另一种真实容器环境。

这证明当前合法存档流可以使用标准 LZO1X 安全接口得到同字节结果，不证明损坏存档上的越界机器行为等价。

## P3 与 P8 的边界

P3 在此确认“如何定位、解压和跨版本停止”，不提前命名大块内部的玩法字段。P8 仍须恢复全部字段语义、旧版本差异、重新序列化顺序，并用原程序验证写回兼容。进入实现门槛中的“至少一个旧存档可完整解析并重新序列化”因此仍未满足。
