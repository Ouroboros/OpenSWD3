# P1 汇编级顶层控制流结论

状态：P1.1 至 P1.8 已完成并交叉复核

日期：2026-08-02

唯一逻辑真值：`swd3.exe` 汇编

IDA 伪码在本阶段只用于定位。以下结论都已回查原 EXE 汇编地址、实际分支、寄存器、栈参数和全局内存读写。

## 1. 阶段结论

P1 完成条件已经满足。

现在可以不依赖 IDA 伪码，完整说明：

```text
PE/CRT 入口
  → WinMain 初始化和窗口创建
  → 自定义启动消息与总初始化
  → Win32 消息泵
  → 空闲分派
      ├─ 视频
      ├─ 暂停
      ├─ 帧抑制 / Sleep(0)
      └─ 单帧主循环
          ├─ 高优先级画面
          ├─ 战斗进入 / 战斗帧 / 战后恢复
          └─ 普通世界 / 剧情 / 特殊模式
  → 各画面分支内部呈现
  → Miles 音频对象维护
  → 关闭请求 / WM_DESTROY / WM_QUIT
  → WinMain 返回 / CRT _exit
```

这只代表顶层控制流已经成为可实现规格，不代表资源格式、剧情完整 opcode、战斗规则、像素算法或存档格式已经完成。

## 2. 启动与窗口

- PE 入口是 `0x0048A740`。
- CRT 在 `0x0048A84E` 调用 `0x00409EC0`。
- `WinMain` 使用四个 32 位参数，并以 `ret 0x10` 返回。
- `WinMain` 注册的窗口过程是 `0x0040A0D0`。
- 主窗口固定创建为 `640×480`。
- `SendMessageA(hWnd, 0x404, 0, 0)` 同步完成启动对话框和总初始化分派。
- 两次独立 `time(NULL)` 分别初始化 CRT `rand` 状态和 250 字 xor 随机状态。
- 正常退出值来自 `GetMessageA == 0` 时的 `msg.wParam`。

详细证据：

- `04-reverse-engineering/evidence/entry-point-0048a740.md`
- `04-reverse-engineering/evidence/winmain-00409ec0.md`
- `04-reverse-engineering/evidence/wndproc-0040a0d0.md`

## 3. 空闲消息泵

没有待处理消息时，`WinMain` 不会无条件调用游戏帧。

它按以下顺序分派：

1. `[0x004CC2AC]` 是全局帧执行门控；F8 手动暂停、剧情 VM 和调试对话框都可改写它。
2. 视频位 `[0x004B7A9C] & 0x20` 优先进入 `0x00484950`。
3. 位 `0x01` 或显示切换门控 `[0x004BABA4] != 0` 时只执行 `Sleep(0)`。
4. 其他正常状态才调用 `0x0040A570`。
5. 帧执行门控为零且显示已恢复时，调用 `0x00411FA0` 绘制并呈现暂停提示。

因此原程序同时存在“消息处理频率”“空闲循环频率”和“达到毫秒门槛的有效游戏帧”三个不同概念。

## 4. 单帧顺序

`0x0040A570` 的顶层顺序已确认：

```text
显示活动门控
  → time(NULL)
  → timeGetTime()
  → 无符号帧间隔判断
  → 帧前倒计时和位迁移
  → DirectInput 设备状态采样
  → 游戏输入边沿与重复状态生成
  → 顶层画面模式互斥分派
  → 音频对象维护
  → 关闭请求检查
```

关键不变量：

- 帧间隔未达到时不更新上一有效帧时刻。
- 游戏按键不是直接由窗口键盘消息驱动；先采样设备，再生成 pressed、held、released 和 repeat 状态。
- 高优先级画面、战斗帧、普通世界/特殊模式帧三者互斥。
- 战斗活动时不会在同一帧继续世界或剧情更新。
- 剧情解释器只在五个顶层门控全部满足时调用。

详细证据：`04-reverse-engineering/evidence/main-frame-0040a570.md`。

## 5. 剧情解释器顶层契约

`0x00427920` 的 P1 入口契约已确认：

- 状态块地址是 `0x004B72A0`，顶层重置范围是 216 字节。
- `+0x20` 是 16 位指令偏移。
- 指令字低 14 位是 opcode；高两位是独立修饰位。
- opcode 由两个跳转表和四个特殊控制值分派。
- 各 handler 自行决定指令长度和偏移推进。
- 两个继续量决定同帧继续取指，或调用 `AIL_serve` 后让出到下一帧。
- Talk 文件打开失败可以直接触发程序销毁路径。

完整 opcode 语义不属于 P1，留到 P5。

详细证据：`04-reverse-engineering/story-vm-entry.md`。

## 6. 战斗顶层契约

`0x00469D20` 的 P1 入口和出口契约已确认：

- `[0x0053CE84]` 是当前战斗指令机器指针。
- 当前操作码是有符号 16 位值。
- 分派范围严格为 `-1..83`，跳转表有 85 项。
- 各 handler 自行保持、推进或改写指令指针。
- 对主循环可见的返回值集合严格为 `{0, 1, 2, 3}`。
- 一保持战斗活动；零、二、三清除战斗活动并进入不同的地图恢复或特殊模式路径。

返回值的最终业务枚举名称和全部战斗 opcode 语义不属于 P1，留到 P7。

详细证据：`04-reverse-engineering/battle-entry.md`。

## 7. 呈现架构的最终 P1 结论

P1.7 推翻了早期的两个错误归类：

- `0x0040CF10` 不是最终呈现。它维护 Miles 的音乐/流、stream、sequence 和 sample 对象。
- `0x00437AE0` 不是普通帧尾。它只在显示恢复阶段执行 surface 恢复和 Blt/Flip 重试。

原程序没有单一顶层 `Present`。已确认的分支内 `Blt` 地址是：

- `0x00408D5E`：高优先级画面。
- `0x00412046`：暂停提示。
- `0x00412716`：普通世界。
- `0x0043A854`：特殊模式一、三至六。
- `0x0044F765`：特殊模式二。
- `0x0045350A`：战斗。
- `0x00484A11`：Bink 视频。

新引擎可以统一 SDL3 呈现接口，但兼容规格必须保留每条分支完成软件绘制、执行呈现和维护音频的相对顺序。

详细证据：`04-reverse-engineering/evidence/presentation-lifecycle.md`。

## 8. 暂停、失焦与恢复

- F8 在 `WM_KEYUP` 中切换 `[0x004CC2AC]`；视频活动时只能强制恢复运行。
- 暂停时不调用正常单帧函数，世界、剧情、战斗、正常输入边沿和帧前时钟迁移均冻结。
- 窗口停用/最小化通过 `0x0040AB50(0)` 停用音频、三套字体 renderer 和战斗显示状态，并设置帧抑制门控。
- 恢复通过 `0x0040AB50(1)` 恢复 DirectDraw surface、三套字体 renderer、surface 行状态和战斗显示状态，再解除门控。
- 完整 `0x0040AB50` 不调用 DirectInput wrapper，也不重新 Acquire 输入设备；此前的“三个输入对象”是对字体 renderer 的错误归类。
- SDL3 重写不需要模拟 surface lost API，但必须复现游戏可见的停用和恢复边界。

## 9. 退出链

延迟关闭链：

```text
[0x004B7A9C] |= 0x04
  → 0x0040A570 尾部 SendMessageA(WM_CLOSE)
  → DefWindowProcA 销毁窗口
  → WndProc 收到 WM_DESTROY
  → 条件化 0x004251B0 完整释放
  → CoUninitialize
  → PostQuitMessage(0)
  → GetMessageA 返回零
  → WinMain 返回 msg.wParam
  → CRT _exit
```

部分初始化、地图和剧情失败会直接同步发送 `WM_DESTROY`，不经过帧尾 `WM_CLOSE`。

原程序没有单独处理 `GetMessageA == -1`；负一也会进入翻译和分发。这一异常行为已经记录，但现代重写应把“兼容结果”和“复制旧 API 错误”分开评审。
