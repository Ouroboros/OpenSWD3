# SWD3 完整重写执行计划

最后更新：2026-08-03

当前阶段：A0 原程序总体架构、模块边界与依赖恢复

当前状态：进行中

## 目标

以 `swd3.exe` 完整汇编为唯一逻辑真值，恢复足以支持 100% 重写的程序规格。

当前先完成原程序总体架构恢复。在 A0 完成前不创建正式重写工程；A0 完成后不再等待所有业务细节一次性调研完毕，而是按模块执行“逆向、规格、UT、实现、汇编复核、真实数据/原程序差分”的闭环。

## 硬约束

1. 汇编是原程序逻辑的唯一真实依据。
2. IDA 伪码只用于定位、辅助阅读和提出假设。
3. 类型、参数、分支、符号扩展、调用约定和数据流必须回查汇编。
4. 伪码与汇编冲突时，无条件以汇编为准。
5. 字符串、资源样本和动态结果只用于解释与验证汇编。
6. 未核对汇编的推断必须标记为“待确认”或“高可信推断”，不得写成“已确认”。
7. 所有调研产物统一放在 `OpenSWD3/analysis/` 下并按类别保存。
8. 每完成一个证据块，立即更新本计划的状态、证据链接和下一步。
9. 新证据推翻旧结论时，先修正文档，再在本计划变更记录中说明原因。
10. 正式重写语言固定为 C++20，构建系统固定为 CMake。
11. 构建和日常开发不得依赖 Visual Studio IDE；默认使用 CMake 命令行与 Ninja。
12. Windows 编译器必须允许在 MSVC 与 LLVM 之间选择，编译器路径不得硬编码进工程文件。
13. 初步还原以 bug-for-bug 的 1:1 行为兼容为目标；原程序的游戏逻辑 BUG 也是规格，不修复。
14. 只有阻断启动或新系统兼容的问题允许做最小修正；修正必须隔离在平台适配层，不得改变玩法、数值、随机调用顺序、帧内顺序、资源解释或存档语义。
15. 每个兼容例外必须记录原汇编行为、旧系统触发条件、新系统失败原因、最小改动和差分验证；不做顺手修 BUG 或主观优化。

## 总体执行方法

本项目不再采用“先把 P5–P8 全部调研完，再一次性开始实现”的瀑布式流程，也不允许在模块边界和状态所有权未知时直接猜测实现。

执行分为两层：

1. 先恢复原程序的全局架构骨架：模块、职责、入口、依赖、状态所有权、生命周期、帧内顺序和平台边界。
2. 架构骨架闭环后，按依赖顺序逐模块执行完整闭环；一个模块达到开始条件即可进入实现，不把其他模块的全部内部细节设为前置条件。

单模块固定循环：

```text
划定汇编函数、全局状态和资产范围
  → 逐汇编恢复数据结构、分支、时序和异常合同
  → 写成可实现规格
  → 从汇编边界和真实数据构造 UT/验证向量
  → 用 C++20 实现
  → 按原地址逐基本块复核实现
  → 运行 UT、真实资产/存档测试和可用的原程序差分
  → 记录残余缺口并验收模块
```

验证必须至少分三层，不能只依赖由同一理解写出的 UT：

- 汇编合同测试：整数宽度、符号扩展、回绕、边界比较、调用顺序、等待/让出和原始 BUG。
- 真实数据测试：使用现有 TSW、ACT、TALK、LMF、ANI、SND 和存档样本。
- 原程序差分：环境具备时比较 framebuffer、状态快照、脚本 IP、随机序列、音视频门控和序列化字节；暂时缺少运行后端时明确记录阻塞，不伪造结果。
